# 多学科就医智助系统

> AI 辅助就医信息整理与多学科决策协作平台
> 把散乱的病历整理成医生看得懂的一页摘要，推演该看哪些科、还缺什么信息，再由医生逐条审核把关。

- 技术栈：Python 3.10+ / Flask / SQLite / 原生 HTML·CSS·JS（**零前端构建、零外链资源**）
- 部署形态：单机本地部署（默认仅监听 `127.0.0.1`）；原始身份信息在本地脱敏，启用外部模型时仅发送脱敏病例文本到配置的模型服务
- 定位：就医信息整理与决策辅助工具，**不提供诊断或处方，不替代医生判断**

---

## 1. 它解决什么问题

就诊者常见的三件难事：

| 问题 | 系统怎么做 |
|---|---|
| 不知道该挂哪个科 | 规则引擎 + 模型受限发言 + 确定性编排三层决策，给出牵头方向与协同科室，每个方向都能展开看命中依据 |
| 资料散乱，三分钟说不清病史 | 病历结构化（每条信息带原文出处）+ 信息缺口清单 + 不超过 3 个关键追问 + 一页摘要 / 完整报告（可打印） |
| 多科意见不一致 | 各专科先独立研判（互相不可见），再聚合共识、单列分歧；分歧可被质询，最终由医生裁决 |

## 2. 能力与边界

**能做**：就医方向建议、资料结构化与摘要、信息缺口提示、就医路径与任务清单、多学科意见聚合与分歧呈现、医生逐条审核与留痕、就诊后资料更新与变化摘要。

**不做（产品红线，写死在代码里）**：

1. **不出诊断**：不给出疾病结论，只输出资料整理结果、方向建议与需要向医生确认的问题；
2. **不出处方**：不涉及药物、剂量与治疗方案推荐；
3. **不输出概率数字**：界面与报告不展示模型自报的置信度或概率；
4. **AI 不覆盖医生**：医生意见与 AI 建议如实并列；患者转述的"医生说……"标为待确认，不作为医生意见采信。

合规话术统一为"建议向医生确认是否需要 ××"，不做指令式医疗行为。

## 3. 快速开始

```powershell
# 1) 建立独立环境并安装项目依赖
python -m venv .venv
.\.venv\bin\python.exe -m pip install -r backend\requirements.txt

# 2) 从模板创建本机配置；修改预置账号密码，不要提交 .env
Copy-Item .env.example .env
# AI_API_KEY 可留空：未配置时直接完成纯规则链路，MDT 状态为 skipped，不启动后台模型任务

# 3) 启动
Set-Location backend
..\.venv\bin\python.exe app.py
```

| 入口 | 地址 | 说明 |
|---|---|---|
| 首页 | http://127.0.0.1:5000/ | 产品介绍与两端入口 |
| 患者端 | http://127.0.0.1:5000/patient | 录入 → 摘要 → 就诊后更新 |
| 医生工作台 | http://127.0.0.1:5000/doctor | 病例审阅 → 逐条审核 → 发布审核版 |

默认兼容账号名为 `patient` / `doctor`，密码必须通过 `.env` 中的
`APP_PATIENT_PASSWORD` / `APP_DOCTOR_PASSWORD` 配置（也可使用 PBKDF2 的
`APP_*_PASSWORD_HASH`）。患者也可以在患者端点击“注册患者账号”自助创建账号，注册成功后会自动登录；
注册接口只会创建 `patient` 角色，不能通过请求体创建医生账号。代码中没有默认密码。

医生账号由部署者预置，并绑定一个主责科室。单医生兼容账号使用 `APP_DOCTOR_DEPARTMENT`；多医生使用
`APP_DOCTOR_ACCOUNTS_JSON`。配置 `access_scope=all` 的总审账号可以查看所有病例，其余医生按科室隔离，例如：

```dotenv
APP_DOCTOR_DEPARTMENT=endocrinology
APP_DOCTOR_ACCOUNTS_JSON=[{"username":"chief_doctor","password":"replace-with-a-strong-password","label":"总审医生","access_scope":"all"},{"username":"doctor_eye","password":"replace-with-a-strong-password","label":"眼科医生","department_code":"ophthalmology"}]
```

`department_code` 必须来自系统科室域。患者确认主责科室并提交后，病例进入该科室医生和总审账号的授权范围；
总审账号通过显式的全量审核范围读取所有病例，科室医生仍以逐病例 `case_access` 为后端权限边界，页面上的科室提示只是可见范围说明。
完整病例接口始终需要账号会话。

游客可通过 `POST /api/guest/session` 获取短期匿名令牌，再使用
`/api/guest/preview` 和 `/api/guest/triage` 体验有限的规则链路。游客不创建病例、
不调用 MDT、不生成审核版报告；会话、输入长度和次数均受限。游客不能把令牌用于
`/api/v2/case/*`。

患者提交审核前会看到系统建议的主责科室，也可以从标准临床科室中调整。提交后页面只显示“已提交至某科室，
等待医生审核”，不显示医生账号。若目标科室暂时没有 active 医生，系统不会写入 submitted 路由，也不会把病例
兜底暴露给其他科室。主责医生在 MDT 初筛中明确选择会诊科室后，才会为对应科室医生建立额外授权；没有医生的
协同科室会记录为待分配。

### 必要安全配置

- 完整病例接口始终强制认证；游客使用独立接口，不能用环境变量重新开启免密访问；
- 免密角色登录已从后端下线，不能用配置重新开启；
- `APP_REVIEWER_MODE=simulation`：比赛版显示“模拟审核员”；真实机构认证接入后才切换为 `clinical`；
- `APP_CORS_ORIGINS`：只填写实际前端来源，不要使用 `*`；
- `AI_CONNECT_TIMEOUT=10` / `AI_READ_TIMEOUT=60`：分别限制连接和读取等待时间；
- `AI_MAX_RETRIES=3` / `AI_MAX_CONCURRENT_REQUESTS=3`：限制模型重试次数与进程内并发请求数；
- 整数配置项填入非数字或超出文档范围时，服务会在启动阶段报出对应变量名并拒绝启动；
- 访问令牌只接受 `Authorization: Bearer ...`，不接受 URL 查询参数；
- 患者只能访问自己创建的病例；无主旧病例不归属任意患者，审核账号也需显式授权。
- 脱敏预览返回短期一次性凭证，创建病例只能消费服务端保存的脱敏文本；每个用户最多保留
  `APP_PREVIEW_MAX_PER_USER=5` 个未消费凭证，全局最多保留 `APP_PREVIEW_MAX_TOTAL=5000` 个。
  达到上限时先清理过期项，再按创建顺序淘汰最早的未消费项；凭证仍绑定用户且只能消费一次。
- 审核账号还必须获得逐病例授权；`APP_AUTO_ASSIGN_REVIEWER=false` 是默认安全配置，
  仅在单审核员演示时显式设为 `true` 自动分配，且自动分配仍按病例主责科室匹配医生，不能全局授权。
- 患者注册按来源地址受 `APP_REGISTRATION_MAX_PER_HOUR` 限制；账号、病例、授权和路由审计都落在本地 SQLite。
- 登录失败按账号与来源地址限流，并限制同一账号活跃会话数；普通凭据失败返回 JSON HTTP 401，
  使用统一的“账号或密码不正确，请稍后重试”提示；进入冷却期时返回 JSON HTTP 429、`code=rate_limited`
  和正整数 `Retry-After`。游客会话创建也有来源地址配额。
- 就诊后更新、追问回答、医生审核修改/理由都会再次经过 PII 校验：手机号、邮箱等阻断型信息拒绝写入，
  姓名/住址等非阻断型信息自动脱敏。

旧版 `/api/start_consultation`、`/api/get_discussion_status/*` 和
`/api/get_all_discussions` 已下线，避免绕过新版鉴权、脱敏和病例状态机。

### Phase 2 单机边界与 HTTP 安全基线

- 模型请求日志只记录元数据（例如异常类型、重试次数、HTTP 状态、响应形状和内容长度），不记录完整
  prompt、模型输出、上游响应 body、API Key 或原始请求异常消息。此约束针对服务端日志；不宣称所有调用方可见的
  错误字符串都已全局改写。
- 每个响应都带 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、
  `Referrer-Policy: strict-origin-when-cross-origin`，以及
  `Content-Security-Policy: base-uri 'self'; object-src 'none'; frame-ancestors 'none'`。
  默认服务是本机 HTTP demo，因此有意不发送 HSTS；这不是 HTTPS 生产部署承诺。
- 会话、预览 token、登录失败计数器和后台工作均为进程内状态。Phase 2 支持的边界是受控机器上的单个进程；
  重启或多进程/多机器部署不能依赖这些状态自动共享。
- 应用只使用 Flask 的 `request.remote_addr` 作为来源地址，不读取或信任 `X-Forwarded-For`、`Forwarded` 等转发头。
  将来接入反向代理时，必须另行定义并审查可信代理、TLS 终止和生产 WSGI 边界。
- Redis、集中式身份与会话、数据生命周期（保留/删除/加密等）、SQL 队列扩展和生产 WSGI 均为延期的生产架构工作，
  不属于本 Phase 2 demo 的已完成能力。

## 4. 一次完整流程

```
录入资料 → 脱敏确认 → 结构化画像 + 智能追问 → 就医方向（S1→S2→S3）
        → 患者确认主责科室并提交审核 → 就医路径与任务 → 多学科分析 → 一页摘要 / 就医详情
        → 医生工作台逐条审核并发布审核版 → 就诊后资料更新 → 变化摘要
```

- **增量原则**：追问回答、就诊后更新只重算受影响模块（分诊 + 路径），未受影响的多学科分析不重跑；
- **状态可回溯**：病例 7 种状态、任务 5 种状态、审核决策逐条留痕，审计时间线可回放。

## 5. 技术架构

### 决策链（可解释优先）

| 段 | 实现 | 作用 |
|---|---|---|
| **S1 规则引擎** | `services/rule_engine.py`（56 条规则 + 科室域 37 门类 + 否定语境识别） | 确定性、可审计；命中强规则即为必选 |
| **S2 模型受限发言** | `services/s2_analyst.py`（仅逐科表态，不得改写规则结论） | 补充规则未覆盖的方向；失败自动降级 |
| **S3 安全约束与编排** | `services/triage.py` | 阈值校验、冲突留痕、数量上限 6、辅助科不做牵头、可靠性分级 |

### 主要模块

| 模块 | 职责 |
|---|---|
| `services/guardrail.py` | 危象拦截（48 条规则 + 组合规则）与非医学内容识别 |
| `services/privacy.py` / `intake.py` | PII 识别打码、录入校验、就医目标 |
| `services/portrait_extractor.py` | 病历结构化（带原文出处 + 直引覆盖率门禁） |
| `services/dependency_matrix.py` | 字段 ↔ 专科映射（追问、路径、缺口填补、影响面分析共用） |
| `services/mdt_analyst.py` / `challenge_service.py` | 独立研判意见卡、聚合与分歧检测、按需质询 |
| `services/evidence_service.py` | 时间线、判断↔证据关联、证据卡（外部依据白名单，不接 RAG） |
| `services/report_service.py` | 一页摘要 + 完整报告（13 段结构，含未审核角标与免责声明） |
| `services/path_service.py` / `task_service.py` | 就医路径与任务中心（显式状态机 + 留痕） |
| `services/review_service.py` | 医生工作台：决策条目枚举、逐条审核状态、发布条件 |
| `services/update_service.py` | 就诊后更新：受影响科室判定、缺口填补、变化摘要 |
| `services/store.py` | SQLite 落盘：用户、病例、科室授权、审计日志、审核决策、状态流转 |
| `services/case_flow.py` | 编排接线层：把上述模块串成完整业务流程 |

### 存储与隐私

- 病例、审计、审核记录保存于本地 SQLite（已在 `.gitignore` 中）；文件库启用 WAL 与 busy timeout，
  降低后台分析和 HTTP 请求并发写入时的锁冲突；
- 进入分析前先做 PII 打码；未配置模型密钥时不调用外部模型，启用外部模型时发送的是脱敏病例文本，不含姓名、电话等直接身份信息；
- 模型请求日志仅保留元数据，不包含完整 prompt、模型输出、上游响应 body、API Key 或原始请求异常消息；
- 病例前端预览最多展示 2000 字，但数据库保存完整脱敏正文（初次病历最多 8000 字，合并正文最多 16000 字），
  不会因展示截断而丢失末尾检查结果；
- 审计表记录每次流程事件与状态流转，异常流转单独标记。
- SQLite JSON 更新在同一锁内原子执行；同一病例的后台分析任务串行化并阻止重复启动。

> Phase 2 的进程内会话、预览 token、登录失败计数器和后台任务只适用于单进程/单机 demo。
> Redis、集中身份与会话、数据生命周期、SQL 队列扩展和生产 WSGI 仍需后续生产架构设计；默认 HTTP 服务不启用 HSTS。
