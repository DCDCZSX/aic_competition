# 《AI 多学科就医咨询助手（MDT）》评测实验设计方案

> 目的：在没有医院资源、旧数据源不确定的情况下，用**公开数据集 + 对比实验**搭出一条可信的证据链，
> 支撑赛题「AI+软件创新」评分里的 **技术实现(20) 与应用价值(15)**，并给创新叙事提供量化数字。

---

## 1. 评测要回答的 4 个问题（每个问题对应一块分数）

| # | 问题 | 评分的哪部分 | 讲故事的方式 |
|---|---|---|---|
| 1 | 分诊准不准——系统判断"该去哪些科"靠谱吗？ | 技术实现 | 分诊准确率 + 与纯 LLM 分诊对比 |
| 2 | 各专科 AI 是不是真"各司其职"、懂本科？ | 技术实现/创新 | 专科题库分科准确率；"自知边界、不乱答" |
| 3 | MDT 比普通单科 AI 问诊多了什么价值？ | 创新性/应用价值 | 同病例对比：单科漏掉的问题 MDT 发现了 |
| 4 | 报告是否结构化、可信、无幻觉硬伤？ | 功能完整性 | 结构化字段完整率 + 坏样本案例说明 |

## 2. 数据集清单（公开、可下载）

| 数据集 | 内容 | 在本方案中的用途 | 获取方式 |
|---|---|---|---|
| **CMB (Chinese Medicine Bench)** | 中文医学多专科考试题（含临床案例），按专科覆盖 | 实验二"专科能力评测"的题库 | [HuggingFace FreedomIntelligence/CMB](https://huggingface.co/datasets/FreedomIntelligence/CMB)（国内可用 hf-mirror.com 镜像） |
| **IMCS21（天池 CBLUE 医疗对话）** | 真实"患者主诉 + 医生问诊"多轮对话 | 实验一/三的患者输入样例库 | [github.com/lemuria-wchen/imcs21-cblue](https://github.com/lemuria-wchen/imcs21-cblue) |
| **Chinese-medical-dialogue-data** | 医患问答大数据集，**含科室字段** | 实验一分诊评测的"金标准科室标签"来源 | GitHub 搜索 `TigerResearch/Chinese-medical-dialogue-data` |
| **cMedQA2 / MedDG 等** | 其他中文医疗问答/单一病种对话 | 备用扩充、单病种纵深案例 | GitHub 搜索名称（NLCorpora 合集有索引：[github.com/Lafitte1573/NLCorpora](https://github.com/Lafitte1573/NLCorpora)） |
| **自建共病案例库**（Plan B） | 参照真实 MDT 常处理的"多病共存/肿瘤复杂病例"构造 20-30 例（如糖尿病+肾病+眼底；慢阻肺+心衰） | 实验三核心素材；若公开数据不顺手用它兜底 | 团队自建 + 请医学背景同学审一遍 |

> ⚠️ 合规：全部用公开/脱敏/自建数据；材料中注明数据来源与用途；展示时对原始对话做改写，不直接贴大数据量原文。
> ⚠️ 下载困难时：HuggingFace 用 `hf-mirror.com` 镜像；天池数据集可能要求报名，GitHub 仓库文件是后备通道。

## 3. 三个子实验

### 实验一：分诊决策评测（验证"判断该去哪些科"）
- 数据：从含科室标签的对话集按科室分层采样，每科 30-50 条主诉，总约 500 条（先做 100 条小样，跑通再扩）
- 输入：患者主诉文本（与线上产品同格式）
- 任务：系统输出 Top-3 建议科室
- 金标准：数据集自带的科室标签
- **指标**：Top-1 命中率、Top-3 命中率、平均建议科室数、常见错分对（如"内分泌↔全科"）
- **对照**：同样的输入丢给"纯 LLM 零样本分诊"，对比你的分诊引擎
- 输出：命中率对比表 + 错分混淆矩阵（答辩图表）
- **这是全项目最早的门禁（Day 3-5）**：若 Top-3 命中率过低，先别往下做，回去改分诊逻辑

### 实验二：专科能力评测（验证"各科 AI 是真专家"）
- 数据：CMB 按专科标签切分，每科 30-50 题
- 任务：①你的"专科 Agent"只答本科题目 ②同题给"通用单科 Agent"
- **指标**：
  - 专科 Agent 在本科目的准确率 vs 通用 Agent（证明专科定位有用）
  - "越界测试"：拿非本科题目问专科 Agent，统计"拒答/转诊率" vs "硬答错误率"（证明它**自知边界**，这是可信医疗 AI 的重要卖点）
- 输出：分科准确率柱状图 + 边界行为统计

### 实验三：MDT 增量价值对比（核心"魔术实验"）
- 数据：多病共存/复杂病例 N≈30（公开对话集中筛多系统症状案例 + 自建共病案例）
- 任务：**同一病例**分别喂给：
  - 对照组 A：普通单科 AI 问诊（只按最相关一科回答）
  - 实验组 B：你的 MDT（分诊 → 多专科协同 → 汇总报告）
- **指标**（建议 1-2 名医学背景同学用 checklist 双盲打分）：
  - 识别的"应就诊专科数"是否更全
  - 结论覆盖度（参考清单：专科建议是否到位）
  - **单科漏项检出数**（MDT 相对单科新增的有效建议条数）← 最重要
  - 报告结构化字段完整率；有无自相矛盾的意见；矛盾处系统是否如实呈现
- 输出：每案例一张"会诊卡"示例 + 汇总统计 + **精选 2-3 个案例做演示素材**

## 4. 工程要求（保证结果可信、可复现）

- 固定：模型型号 / temperature=0 / 随机种子，全部记录在 config
- 每次评测把输入输出**完整落盘**（答辩截图证据）
- 记录 token 消耗与单次成本（顺手做"低成本"叙事）
- 脚本骨架：Python，每个实验一个脚本 + 一个共享评测框架（读数据 → 跑系统 → 评分 → 出表）
- 数据集与评测集版本化（文件夹带日期）

## 5. 结果如何翻译成"评分语言"（写进技术方案）

- 实验一 → "分诊 Top-3 命中率 X%，较纯 LLM 提升 Y 个百分点" → 支撑技术实现
- 实验二 → "专科 Agent 在本科准确率 X%，越界拒答率 Y%" → 支撑"多智能体各司其职"创新叙事
- 实验三 → "在 N 个共病病例中，MDT 平均比单科问诊多检出 Z 项潜在就诊建议" → 支撑应用价值 + 社会价值（复杂患者少漏诊、少跑路）
- 附 1-2 个"典型案例会诊卡"全页展示 → 演示视频与 PPT 的素材

## 6. 时间安排（4 周内穿插完成）

| 时间 | 任务 |
|---|---|
| Day 1-2 | 数据下载与清洗（对话集 + CMB），构造小样测试集（先 100 条） |
| Day 3-5 | **实验一小样跑通 + 门禁判定**（分诊逻辑不行就先改它） |
| Week 2 | 实验一扩量 + 实验二（专科题库评测） |
| Week 3 | 实验三（对比实验 + 人工打分）+ 精选案例 + 图表化 |
| Week 4 | 结果汇总进技术方案文档与演示视频 |

## 7. 风险与兜底

| 风险 | 兜底 |
|---|---|
| 公开数据集下载/格式不顺 | 先只做实验三 + 自建 20-30 例共病案例库，三个实验不必全做，但实验三必须做（它是演示核心） |
| 没有医学背景评分人 | 找高年级临床/护理/生物医学同学；评分表做成 checklist 降低门槛；至少由小组用统一清单双盲各评一遍 |
| 分诊效果不理想 | 这是好事——它告诉你该补规则库了；分诊引擎本来就是自研部件 |
| LLM 生成不稳定 | temperature=0 + 固定版本模型 + 结构化 JSON 输出 + 坏样本人工复核 |

## 8. 流程影响评测（任务 9）

前面的实验回答的是分诊、专科边界和 MDT 内容覆盖问题，不能直接回答“患者和医生是否更省力”。流程影响单独使用同一批脱敏病例的配对对照：每个 `pair_id` 在人工整理组和系统辅助组各完成一次相同任务，参与者按随机或拉丁方顺序执行，清除上一条件的页面状态。患者端另记录当前四阶段流程和一页摘要的查找/理解任务；医生端记录必审条目和实际审核操作。

### 8.1 记录和工具

- 记录格式固定为 `workflow-impact.v1` JSONL；字段白名单、计时起止点和排除规则见 `docs/评测流程影响数据字典.md`。
- 汇总脚本为 `backend/eval_workflow_impact.py`。它只读取匿名 ID、结构化计时、操作数和 1–5 分评分，拒绝病例正文、报告正文和未知自由文本字段。
- 推荐命令：

  ```powershell
  python backend/eval_workflow_impact.py `
    --input backend/tests/fixtures/workflow_impact_dry_run.jsonl `
    --output eval_out/workflow_impact_dry_run.md `
    --json-output eval_out/workflow_impact_dry_run.json `
    --dataset-label dry-run `
    --evidence-status dry_run `
    --fail-on-invalid
  ```

- 输出必须同时列出有效记录、完成/失败/排除状态、配对分母、缺一侧、重复、协议偏离和字段校验错误；没有适用字段时输出“未记录”，不能补成零。

### 8.2 指标定义

| 对象 | 指标 | 分母/口径 |
|---|---|---|
| 患者 | 四阶段完成率、总耗时、返回/错误次数 | 每条件有效启动记录；阶段分别计算 |
| 患者 | 摘要查找完成率、可读性、下一步理解度 | 查找任务总数；评分 1–5，报告 n、均值、中位数 |
| 医生 | 实际审核耗时、必审覆盖率 | 完成病例；`reviewed_items / required_review_items` |
| 医生 | 修改率、驳回率 | 已作出决定的条目；不把未审条目视为接受 |
| 医生 | 分歧处理完成率、资料往返次数 | 有分歧病例 / 记录到往返的病例 |
| 医生 | 专科呈现覆盖 | 任务清单应覆盖科室数；不表述为临床召回率 |

配对耗时差值定义为“系统组 − 人工组”，只纳入同一 `pair_id` 下两侧均完成且无协议偏离的观察。评测结果在真实人工数据采集前只能标记为 `dry_run`，不能宣称系统节省时间、提升临床效果或改善诊断。
