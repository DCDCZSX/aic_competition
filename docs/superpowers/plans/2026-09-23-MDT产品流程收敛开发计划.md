# MDT 产品流程收敛开发计划

> **执行说明：** 按任务顺序逐项实施，并在每项完成后检查验收结果。用户明确要求开始执行之前，不要开始修改业务代码。每项任务都应能单独检查和验收。

**目标：** 将已确认的产品功能整理成一条完整的比赛版流程：患者准备资料、医生判断是否进入 MDT、医生聚焦审核重点、发布带版本的审核报告，并在资料更新后只复核受影响内容。患者端另按四个易懂阶段组织操作，并以精简的一页就医摘要作为默认阅读结果。

**实现方式：** 复用现有 Flask、SQLite 和 `CaseFlow` 流程；增加由医生负责的 MDT 初筛子流程；病例生命周期继续使用现有状态机，MDT 初筛结果单独保存；AI 专科参考意见与医生决定分开展示；报告发布时保存不可变的内容快照。比赛版继续使用一个医生账号承载演示职责；独立专科医生账号、真实排班和医院系统对接留到试点阶段。

**技术栈：** Python 3.10+、Flask、SQLite、unittest、原生 HTML/CSS/JavaScript，以及现有 `backend/services` 架构。

**产品范围依据：** [`../../产品功能最终版-评委问答与功能边界.md`](../../产品功能最终版-评委问答与功能边界.md)  
**进度记录主文件：** [`../../../../开发进度与交接.md`](../../../../开发进度与交接.md)（工作区根目录；实际实施后更新 §5 和变更日志）。

## 全程约束

- 保持产品边界：系统不提供诊断、处方、治疗医嘱或急救处置，也不替代医院现有系统。
- 模型生成的专科内容必须标注为“专科 AI 参考意见”，不能显示成真实专科医生意见。
- 只有医生角色可以作出 MDT 初筛决定、处理审核项或发布审核版。
- 尚未解决的专科分歧要在报告中显示状态和下一步处理方式，不能由系统悄悄合并。
- 急症安全拦截始终优先于普通录入、MDT 初筛和报告流程。
- 不得自动向医生开放全部患者病例。沿用明确授权边界；单审核人自动分配只用于显式配置的比赛演示环境。
- 不得只凭大模型置信度降低审核要求。尚未分类的项目继续由医生处理，直到有经过临床审核的规则。
- 保持已有 SQLite 数据库可读取。新增结构时使用可重复执行的迁移；不得删除或改写历史审核决定和审计记录。
- 比赛版不新增医院身份认证、排班、计费、HIS/EMR/PACS/LIS 对接或实时协作。
- 工作流评估不得保存可识别患者身份的信息或患者原始文本。

## 仓库基线与文件职责

- `backend/app.py`：需要身份验证的接口和输入校验。
- `backend/services/case_flow.py`：病例流程编排、访问授权、审核发布和资料更新影响处理。
- `backend/services/case_state.py`：现有病例生命周期状态；MDT 初筛决定与病例状态分开管理。
- `backend/services/store.py`：SQLite 持久化和向后兼容的数据库初始化。
- `backend/services/review_service.py`：审核项、审核决定、当前审核轮次的处理状态和汇总。
- `backend/services/update_service.py`：受影响字段/科室的判断和变化摘要。
- `backend/services/report_service.py`：患者摘要和完整报告的数据生成。
- `backend/templates/patient.html`：患者流程、状态、报告版本和变化展示。
- `backend/templates/doctor.html`：医生队列、MDT 初筛、重点审核和发布流程。
- `backend/static/css/dsh.css`、`backend/static/css/tokens.css`：患者端和医生工作台共用的界面组件与样式尺度。
- `backend/tests/`：变更行为对应的单元测试和 HTTP 回归测试。
- `backend/verify_doctor_http.py`、`backend/verify_update_http.py`、`backend/verify_report_render.mjs`：现有端到端验收工具。
- `../../开发进度与交接.md`：工作区根目录进度主文件在仓库内的副本；按项目约定，在提交 PR 前同步。

## 本轮执行阶段总览

本轮不按文件顺序零散修改，而按下面五个阶段推进。每个阶段先完成自己的验收门槛，再进入下一阶段；阶段内的任务可以在不改变依赖关系的前提下拆成多个小提交。

| 阶段 | 名称 | 对应任务 | 主要结果 | 进入下一阶段的条件 |
|---|---|---|---|---|
| 阶段 0 | 基线与范围冻结 | 任务 0 | 确认当前分支、未提交改动、现有验证基线和比赛版边界 | 基线记录完成；未把旧测试数字误当成本轮结果；范围和风险审核口径明确 |
| 阶段 1 | 患者端流程收敛 | 任务 1、7、8 | 报告状态说清楚；九个内部页面真正合并为四个阶段；一页摘要精简；侧栏和视觉噪声减少 | 患者可按四阶段走通；重要安全信息仍可见；摘要和完整详情都能访问；宽窄屏结构检查通过 |
| 阶段 2 | 医生端 MDT 工作流 | 任务 2、3、4 | 医生先做 MDT 初筛；形成会前资料包；AI 参考意见、必审项和抽查项分开 | 医生可以完成初筛、查看资料包、聚焦必审项；病例权限和审计记录有效 |
| 阶段 3 | 版本、分歧与增量复核 | 任务 5、6 | 分歧由医生留痕处理；报告版本不可变；新增资料只重开受影响审核项 | 连续发布、更新和复核场景可追溯；历史版本不被改写；无关决定不被误重开 |
| 阶段 4 | 整体验收与价值评估 | 任务 9 + 最终交付验收 | 走通完整演示链路，记录患者流程和医生工作量指标 | 验收工具通过；评估报告写清样本、指标、失败和局限；进度文档反映真实状态 |

### 推荐执行顺序

1. **先做阶段 0**：不改变产品行为，只建立基线和边界。
2. **再做阶段 1**：先统一报告阶段语义，再合并四阶段页面，最后精简摘要和视觉层级；这样患者端先形成稳定入口，后面的医生流程才有明确的患者侧状态承接。
3. **阶段 2 接着做**：把现有医生审核台前面补上 MDT 初筛和会前资料包，再收紧审核分级；不要先做自动免审规则扩张。
4. **阶段 3 最后实现业务闭环**：先保证医生决定、分歧和发布版本可追踪，再把资料更新映射到具体审核项。
5. **阶段 4 只在前面闭环后进行**：不提前宣称节省时间或临床有效，先按定义好的指标记录实际结果。

阶段 0 和阶段 1 已完成；阶段 2 的任务 2（MDT 初筛与病例分流）已完成，任务 3、4 及阶段 3–4 尚未开始。本文件和进度表区分计划、基线和业务实现。阶段 0 和阶段 1 的证据分别见 2026-09-24-阶段0基线记录.md 与 2026-09-24-阶段1患者端收敛记录.md；任务 2 的实现与测试记录见 2026-09-25-任务2-mdt初筛工作流.md。

**现状与设计方向：**

- 当前已经有“一页就医摘要”和“完整报告”两个视图；完整报告包含 13 段，并默认逐段折叠。因此本任务重点是让精简摘要成为患者最清楚、最容易找到的默认结果，并减少摘要里的重复和低价值内容。
- 摘要优先回答患者和接诊医生最需要快速确认的事项：主要就诊问题、关键已知资料、仍需补充或核对的信息、建议咨询方向和需要向医生确认的问题、下一步任务。
- 完整证据、资料出处、专科 AI 分析和技术解释仍可查看；通过“为什么这样分析”“查看完整资料”等清楚入口按需展开。

- [x] 先增加报告检查：患者默认进入一页摘要；完整报告不会抢占默认视图；医生审核状态和版本仍清楚可见。
- [x] 精简一页摘要，合并重复信息；缺口只突出会影响下一步准备或就医判断的内容，普通空项不反复显示“暂无”。
- [x] 评估“结果可靠性”“规则校验说明”等内容对患者下一步行动是否有帮助；若只是内部技术信息或容易引起误解，移到“为什么这样分析”或医生详情中，不放在默认摘要。
- [x] 对较长的任务、问题或已知资料设置默认展示数量；超出部分使用明确的“展开更多”，不得截断关键信息且不提供查看方式。
- [x] 将证据出处、分科 AI 视角、详细时间线和技术校验说明放到按需展开的详情区；入口使用患者看得懂的文案，例如“为什么这样分析”。
- [x] 急症提示、未审核状态、未解决分歧、重要资料缺口和医学用途边界保持清楚可见，不因追求简短而删除或弱化。
- [x] 检查医生工作台的队列 → 病例 → 审核流程：在当前结构上减少不必要的来回切屏，让病例选择、待处理重点和下一项审核操作连续可达；保留医生所需的证据和审计信息。
- [x] 工作台标题统一使用易读的无衬线字体；首页可以保留品牌衬线字。正文和关键辅助说明至少 14px；仅非关键时间戳等元信息可以使用更小字号，并核对对比度和缩放可读性。
- [x] 每个患者阶段和医生主要视图只保留一个主要操作按钮；返回、展开详情、导出等操作使用次级视觉样式。
- [x] 减少嵌套卡片和重复边框。以当前首屏为基线，将不承担分组或状态表达作用的边框数量减少约 30%–40% 作为视觉检查目标；保留风险提示、选中态和必要分区的边界。
- [x] 核对列表筛选下拉控件。当前通用 `select` 外框已使用 12px 圆角；先确认实际问题发生在控件外框还是浏览器/系统绘制的展开选项菜单。若确需统一菜单圆角，再评估可访问的自定义列表框，并覆盖键盘操作、焦点、读屏语义和窄屏使用。
- [x] 运行报告、结构和渲染检查；在宽屏与窄屏各检查一次信息层级、字体、按钮主次、展开详情和打印结果。

**验收标准：** 患者打开报告即可先看到一页、重点明确的摘要；更深的分析仍可按需查阅。患者端和医生工作台各页面都有清楚的主操作，正文可读，重复边框明显减少，重要安全与证据内容仍可访问。
