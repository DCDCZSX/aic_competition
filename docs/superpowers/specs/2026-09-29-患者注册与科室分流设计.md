# 患者注册与科室分流设计

日期：2026-09-29  
范围：比赛版第一阶段（患者注册、预置多科室医生、病例按主责科室进入医生队列）

## 1. 背景与目标

当前系统已经有患者病例所有权、逐病例 `case_access` 授权和医生审核队列，但账号仍由环境变量提供的一个患者账号与一个医生账号组成。病例的分诊结果也已经包含主责科室与协同科室，但患者端没有注册入口，医生账号没有持久化的科室归属，病例提交后无法按科室稳定分流。

本次设计的目标是：

1. 患者可以创建自己的账号并登录；
2. 医生账号由部署者预置，绑定一个主责科室，不开放公开注册；
3. 患者确认主责科室后，病例只授权给该科室的医生；
4. 患者不会因为选择主责科室而自动把病例暴露给所有协同科室；
5. 主责医生后续可以通过现有 MDT 初筛流程按需邀请协同科室；
6. 保留现有环境变量账号、测试夹具和旧病例的兼容性；
7. 所有注册、分流、授权和撤回均可审计，权限必须由后端执行。

## 2. 明确的产品边界

### 2.1 本阶段包含

- 患者自助注册：用户名 + 密码，注册后自动登录；
- 患者账号只允许创建 `patient` 角色，客户端不能注册医生；
- SQLite 持久化用户账号，密码只保存 PBKDF2-SHA256 哈希；
- 预置多个医生账号，每个医生绑定一个标准科室；
- 患者在报告阶段确认主责科室，提交后病例进入该科室医生队列；
- 患者只能看到“已提交至某科室”等安全状态，不看到医生账号；
- 医生队列仍由现有 `case_access` 授权过滤；
- 重复提交幂等，不重复创建授权；
- 没有可用医生时不改变病例提交状态，并返回可解释错误；
- 现有 `APP_DOCTOR_USERNAME` / `APP_DOCTOR_PASSWORD` 继续可用。

### 2.2 本阶段不包含

- 医生公开注册、医生执业资质核验、短信/邮箱验证；
- 找回密码、二次认证、医院统一身份认证；
- 多医院租户隔离；
- 患者直接选择任意协同科室并授予访问权；
- 将模型推荐的所有科室自动授权给对应医生；
- 把比赛版本地认证宣称为生产级医疗身份认证。

## 3. 核心业务规则

### 3.1 患者注册与登录

- 注册接口只创建患者角色；请求中的 `role` 字段若存在必须拒绝，避免角色升级。
- 用户名规范为 3–64 个 ASCII 字符（字母、数字、`.`、`_`、`-`），按原样唯一；密码长度为 8–128 个字符。
- 注册成功返回患者会话，前端直接进入患者端；重复用户名返回 `409 username_taken`，不区分账号存在的其他敏感信息。
- 患者显示名可选，默认“就诊者”；不在注册阶段收集身份证、手机号等非必要身份信息。
- 登录继续使用统一的模糊错误信息和已有失败限流。
- 注册按来源地址限流，默认每小时最多 20 次，可由 `APP_REGISTRATION_MAX_PER_HOUR` 调整；超限返回 `429`。

### 3.2 医生账号

- 医生账号只能由环境变量配置或部署初始化时写入用户表。
- 每个医生账号有 `department_code`，必须解析到 `services.department_domain` 的标准科室。
- 兼容旧的单医生环境变量：`APP_DOCTOR_USERNAME`、`APP_DOCTOR_PASSWORD`；新增 `APP_DOCTOR_DEPARTMENT`。
- 多医生通过 `APP_DOCTOR_ACCOUNTS_JSON` 配置，格式为对象数组：

  ```json
  [
    {"username":"doctor_endocrine","password":"...","label":"内分泌科医生","department_code":"endocrinology"},
    {"username":"doctor_oph","password":"...","label":"眼科医生","department_code":"ophthalmology"}
  ]
  ```

- 配置中的医生账号在启动时幂等写入用户表；已有账号不因每次启动而覆盖密码或科室。
- 医生会话可安全返回 `department_code` 和科室名称，患者接口不得返回医生用户名或内部授权字段。

### 3.3 科室确认与病例分流

- 系统分诊仍产生 `primary` 与 `secondary` 科室。患者不是被迫凭经验选择科室，而是确认系统给出的主责科室，也可以从标准可牵头科室中改选。
- 患者提交时保存：
  - `triage_primary_department`：系统原始主责科室；
  - `requested_department`：患者确认的主责科室；
  - `submitted_at` 与 `submission_status`。
- 默认只把病例授权给 `requested_department` 对应的医生。
- 患者改选与系统建议不一致时，保留差异供医生查看，不阻断提交，但标记为“患者调整过分诊方向”。
- 没有可牵头科室或无法解析科室时，患者必须先修改资料或使用系统给出的有效主责科室；不静默分给所有医生。
- 急症仍遵循现有急救拦截与急诊提示，不进入普通科室审核队列。

### 3.4 MDT 访问边界

- 模型产生的协同科室意见不等于这些科室已经获得病例访问权。
- 只有主责医生在 MDT 初筛中明确建议并选择协同科室时，系统才为这些科室的 active 医生建立额外授权；`single_specialty`、`need_more_info` 和 `urgent_care` 不新增协同科室授权。
- MDT 选择的科室没有可用医生时，初筛记录仍可保存，但审计中记录“等待该科室医生配置”，不把病例授权给其他科室代替。
- 未被邀请的其他科室医生即使登录，也不能读取病例详情。

## 4. 数据模型

### 4.1 `users`

在现有 SQLite `Store` 中增加：

```text
users
- username TEXT PRIMARY KEY
- password_hash TEXT NOT NULL
- role TEXT NOT NULL                 -- patient / doctor
- label TEXT NOT NULL
- department_code TEXT               -- 患者为空；医生必填且为标准科室 code
- status TEXT NOT NULL DEFAULT 'active'
- created_at TEXT NOT NULL
- updated_at TEXT NOT NULL
```

索引：`(role, status)` 与 `(role, department_code, status)`。

旧的环境变量账号仍可作为启动种子。为了兼容测试中直接传入 `AuthService(accounts=...)` 的用法，内存账号夹具继续保留，不强制所有单测改成数据库账号。

### 4.2 `cases` 的路由元数据

不新增破坏现有状态机的病例状态。将下列内容放入病例 `payload.routing`，避免把分析状态和审核提交状态混为一谈：

```json
{
  "status": "not_submitted | submitted | in_review | returned | confirmed",
  "triage_primary_department": {"code":"...", "name":"..."},
  "requested_department": {"code":"...", "name":"..."},
  "patient_adjusted": false,
  "submitted_at": "..."
}
```

`case_state` 仍由原有分析/审核状态机维护；医生是否能看到病例仍以 `case_access` 为硬权限边界。

## 5. 后端接口

### 5.1 `POST /api/register`

请求：

```json
{"username":"alice_01","password":"a-strong-password","label":"就诊者"}
```

成功：`201`，返回 `status`、患者安全会话和 scopes；不返回密码、哈希或医生字段。

错误：

- `400 invalid_request`：用户名/密码不符合格式；
- `409 username_taken`：用户名已存在；
- `429 rate_limited`：触发 `APP_REGISTRATION_MAX_PER_HOUR` 注册频率限制；
- `500 internal_error`：不回显 SQLite 或哈希内部异常。

### 5.2 `POST /api/v2/case/<case_id>/submit-review`

患者本人调用。请求体允许传标准 `department_code`；缺省时使用系统分诊的主责科室。

服务端流程：

1. `_guard_case(case_id, 'case:own')` 验证病例归属；
2. 通过 `department_domain.resolve` 和 `can_be_primary` 校验科室；
3. 查询该科室 active 医生账号；
4. 无可用医生时返回 `409 no_reviewer_available`，不改变 `routing.status`；
5. 更新 `payload.routing`；
6. 对匹配医生逐个调用现有 `grant_case_access`；
7. 写入 `case_submitted_for_review` 审计事件；
8. 返回科室名称、状态和授权数量，不返回 reviewer 用户名。

重复调用必须返回成功的当前状态，不产生重复授权或重复病例；如果患者传入不同科室，已提交病例不允许静默改路由，需先撤回或由后续管理员流程处理。

### 5.3 `GET /api/departments`

返回可供患者确认的标准可牵头科室（不返回辅助科作为主责选项），包含 `code`、`name`、`group`。该列表来自 `department_domain`，不在前端另维护一份。

### 5.4 现有接口调整

- `/api/login` 从数据库用户和兼容内存账号读取账号；会话安全字段可增加医生科室信息。
- `/api/me` 返回当前会话的安全科室字段（医生才有）。
- `/api/v2/cases` 继续通过 `case_access` 返回病例；医生端显示当前登录医生科室。
- `/api/v2/case/<id>/mdt-screening` 在 `recommend_mdt` 且科室校验通过后，为选定协同科室的 active 医生建立 `case_access`，返回已授权的科室数量；病例详情仍只返回给实际获得授权的医生。
- `/api/v2/case/<id>/access` 保留给兼容测试/受控内部流程，患者端不再直接提交任意 `reviewer_id`。
- `APP_AUTO_ASSIGN_REVIEWER` 默认仍为 `false`。若显式开启，自动分配也必须按照病例主责科室匹配医生，不能全局授权。

## 6. 前端改动

### 6.1 患者端

- 登录卡增加“注册患者账号”切换入口；注册表单含用户名、密码、确认密码和可选显示名。
- 注册成功自动进入患者流程；错误消息使用现有 `role=alert` / `aria-live` 语义。
- 报告/就医详情阶段增加“提交给对应科室医生审核”卡片：
  - 展示系统推荐主责科室；
  - 提供标准科室选择；
  - 明确提示“提交后仅该科室医生可见”；
  - 提交前显示患者调整提示（如有）；
  - 提交后显示“已提交至 X 科，等待医生审核”。
- 患者端不显示 reviewer_id、医生账号、授权表细节。

### 6.2 医生端

- 登录后在身份区域显示医生科室；
- 队列顶部显示“当前科室：X”；
- 保留现有风险排序与病例筛选，不把科室过滤当作权限校验；
- 队列空状态说明当前科室暂无已提交病例。

## 7. 迁移与兼容

- `Store._init_schema()` 使用 `CREATE TABLE IF NOT EXISTS` 和 `PRAGMA table_info` 增量创建 `users`，不删除旧表。
- 启动种子只在用户名不存在时写入，确保现有数据库和现有账号继续可登录。
- 旧病例 `payload.routing` 缺失时视为 `not_submitted`；已有 `case_access` 授权不被撤销。
- 旧的单医生测试账号未配置科室时继续允许显式 `case_access` 访问；新患者提交分流要求目标医生有有效科室。
- `.env.example` 增加 `APP_DOCTOR_DEPARTMENT`、`APP_DOCTOR_ACCOUNTS_JSON` 和注册限制说明。

## 8. 测试与验收

### 后端

- 注册成功、重复用户名、非法用户名、弱密码、角色升级字段被拒绝；
- 注册后能登录并只能访问自己的病例；
- 密码只保存哈希，响应和日志不包含明文密码；
- 医生种子账号能返回正确科室；
- 患者提交默认主责科室成功；患者选择有效其他主责科室成功并记录调整；
- 非病例所有者不能提交；无可用医生时不写入 submitted 状态；
- 重复提交幂等；已提交病例不能被患者静默改路由；
- 内分泌病例不会出现在眼科医生队列，眼科病例不会出现在内分泌医生队列；
- 医生访问未授权病例仍返回 404；患者响应不含 reviewer_id；
- 旧 `case_access`、旧单账号登录和游客链路回归通过。

### 前端

- 患者页面包含登录/注册切换、注册字段和注册错误区域；
- 报告阶段只存在一个明确的提交审核主操作，不重复引入旧的左侧目录；
- 提交状态和科室提示可被键盘及读屏器感知；
- 医生页面展示登录医生科室和空队列状态。

### 手工验收路径

1. 注册患者账号并登录；
2. 创建病例并完成分诊；
3. 患者确认“内分泌科”，提交审核；
4. 用内分泌科医生账号登录，病例出现在队列；
5. 用眼科医生账号登录，病例不可见；
6. 患者重新提交同一病例，授权数量和病例数不增加；
7. 医生发起 MDT 后，只有明确邀请的协同科室获得访问权。

## 9. 实施顺序

1. Store 用户表、用户读写方法和密码哈希兼容；
2. AuthService 数据库账号读取、医生种子配置和患者注册接口；
3. 科室列表接口、病例提交审核接口及路由审计；
4. 患者端注册/登录切换与科室确认卡片；
5. 医生端科室身份和队列提示；
6. 先写失败测试，再实现接口与页面；
7. 运行聚焦测试、现有前端静态测试、编译检查和可用的端到端验证。
