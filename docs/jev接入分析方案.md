# Jev 接入多学科就医智助系统的分析与验证方案

> 文档日期：2026-09-22  
> 适用项目：CHAIS 多学科就医智助系统  
> 当前结论：建议先做离线 A/B 验证，再决定是否灰度接入；不建议直接替换现有生成型模型。

## 1. 文档目的

本文用于回答三个问题：

1. Jev 是否适合当前系统的模型任务；
2. 如果适合，应该接入哪一层；
3. 如何在不破坏现有安全边界的情况下验证它是否真的带来收益。

本文是技术分析和验证方案，不构成医疗器械、临床诊断或生产合规结论。

## 2. 当前系统概况

当前主链路为：

```text
患者输入
  → 病例画像与信息补全
  → S1 规则分诊
  → S2 模型受限发言
  → S3 确定性决策编排
  → 就医路径与任务
  → 多专科意见卡、质询与医生审核
```

主要代码位置：

| 模块 | 位置 | 当前职责 |
|---|---|---|
| 模型调用 | `backend/services/ai_service.py` | OpenAI 兼容网关、重试、超时、结构化输出调用 |
| S2 受限发言 | `backend/services/s2_analyst.py` | 对规则候选科室逐科表态，可补充、接受或反驳 |
| S3 分诊编排 | `backend/services/triage.py` | 规则与模型结果合并、阈值、排序、强规则保护 |
| MDT 意见卡 | `backend/services/mdt_analyst.py` | 生成专科事实、推断、检查建议、信息缺口和质询 |
| 规则层 | `backend/services/rule_engine.py` | 急症拦截、科室候选和规则证据 |

当前系统的几个关键边界：

- S1 规则层已经承担主要分诊责任；
- 模型不能删除强规则命中；
- 新增科室受模型置信度阈值限制；
- 模型调用失败会退回纯规则路径；
- 最终报告需要经过医生审核；
- 当前模型输出中的置信度主要用于内部编排，不直接展示给患者。

现有评测中，完整链路的 Macro 召回为 0.964，纯规则为 0.954，纯 LLM 选科的精确率明显低于规则和完整链路。由此可见，当前主要问题不是简单地“换一个更大的生成模型”，而是如何提高长病历处理、规则误触发修正和结构化决策的稳定性。

## 3. Jev 能力概览

Jev 是 TypeSafe AI 在 2026 年 9 月发布的 System One 模型，定位是让软件直接消费结构化判断，而不是先生成文本、再解析 JSON。

官方接口提供三类问题：

- `Choice`：从有限选项中选择一个，返回选项概率和置信度；
- `Score`：在预设等级上评分，返回等级概率和置信度；
- `Noul`：判断一个陈述为真的概率。

官方文档和当前模型信息显示：

- 当前版本为 `jev-1.13.0`；
- `jev-latest` 是会随发布变化的别名；
- 输入是文本或 JSON，不支持图片、音频、视频；
- 官方称输入价格为每百万 token 约 0.042 美元，输出不单独收费；
- 当前处于 early access 阶段；
- 官方说明英语准确度最好，中文等 CJK 语言需要自行验证；
- 官方列出的弱点包括数字精确计算、日期比较、复杂间接推理、冗长无关上下文和生成文本。

官方资料：

- [TypeSafe AI 介绍](https://docs.typesafe.ai/introduction)
- [API 快速开始](https://docs.typesafe.ai/introduction/quickstart)
- [模型信息与版本](https://docs.typesafe.ai/models)
- [Jev 1.13 已知限制](https://docs.typesafe.ai/model-jaggedness/jev-1.13)
- [TypeSafe 官方发布说明](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

### 3.1 需要避免的误解

Jev 的类型安全只说明返回值符合预定义结构，不等于医学判断正确，也不等于临床风险为零。

同样，Jev 返回的概率和置信度不能简单等同于当前系统中的模型自报置信度：

- `Choice` 概率是有限选项之间的相对判断；
- `Noul` 是某个陈述为真的概率；
- 不同类型的问题不能默认共用同一个阈值；
- 多个独立 `Noul` 的概率也不保证加和为 1。

## 4. 接入适配度判断

| 系统模块 | 适配度 | 判断 |
|---|---:|---|
| S1 规则分诊 | 低 | 规则承担确定性安全边界，不应由 Jev 替换 |
| S2 候选科室复核 | 高 | 属于有限选项和原子判断，最适合优先验证 |
| S3 阈值与编排 | 高 | Jev 可提供判断信号，但最终逻辑必须留在代码中 |
| 急症拦截 | 中 | 可作辅助判断，不能替代现有急症规则 |
| MDT 意见卡生成 | 低 | Jev 不适合生成事实说明、理由和自然语言建议 |
| 患者端解释文本 | 低 | 继续使用生成模型或确定性模板 |
| 模型输出质量审核 | 高 | 可用 `Noul`/`Choice` 做结构化复核 |
| 医生审核分流 | 高 | 可用 confidence 触发人工复核，但需要重新校准 |
| 中文长病历抽取 | 未知 | 必须使用真实中文样本单独评测 |

## 5. 推荐的接入位置

### 5.1 首选：S1 规则命中复核

当前真实长病历存在关键词过触发：既往史、会诊经过或查体中的词汇可能导致无关科室被命中，挤占有限的推荐名额。

可以让 Jev 对每个规则命中做原子判断：

```text
给定病例片段、命中的规则和规则对应的医学条件：
这段文字是否真的表达了该条件？
```

输出可以用于：

- 给规则命中降权；
- 标记“需要人工复核”；
- 识别既往史或会诊经过造成的弱相关命中；
- 帮助分析规则误报原因。

强规则，尤其是急症规则，不应被 Jev 单独否决。

### 5.2 首选：S2 候选科室结构化判断

当前 S2 输出包含 `stance`、`confidence` 和自然语言 `reason`。Jev 可以承担其中的结构化判断部分：

```text
对于“眼科”：
这个病例是否存在需要眼科参与的明确证据？

对于“血液科”：
这个病例是否存在血液系统异常，需要血液科参与？

对于“感染科”：
这个病例是否存在感染性问题，需要感染科参与？
```

然后由现有 S3 代码继续负责：

- 阈值判断；
- 强规则覆盖；
- 最多 6 个科室；
- 牵头科确定；
- 冲突留痕；
- 医生审核。

Jev 可以减少自由生成 JSON 的解析失败，但不能自动产生完整的医学理由。需要展示给医生的理由仍可由现有生成模型提供，或由规则证据模板生成。

### 5.3 辅助：急症和风险升级判断

可以增加以下辅助问题：

- 是否包含意识改变、严重呼吸困难、活动性大出血等危险信号；
- 是否需要立即人工审核；
- 是否存在输入信息不足但风险不能排除的情况。

这些结果只能作为辅助信号。现有急症规则和医生审核门禁仍然是主安全边界。

### 5.4 辅助：模型输出质量检查

对于现有生成模型生成的意见卡，可以让 Jev 做离散校验：

- 该意见卡是否支持当前选中的科室；
- 推断是否超出给定事实；
- 是否出现未经授权的治疗方案或诊断式结论；
- 是否需要医生确认；
- 是否存在明显的事实与结论冲突。

这类任务不要求 Jev 生成文本，适合其结构化判断模式。

## 6. 不建议的接入方式

### 6.1 不直接替换 `AIService`

现有 `AIService` 面向的是：

```text
messages → 生成文本 → JSON 恢复与字段校验
```

Jev 面向的是：

```text
state + typed questions → typed answers
```

建议增加独立的 `TypeSafeDecisionService`，不要把 Jev 响应硬塞进现有 JSON 恢复逻辑。

推荐结构：

```text
AIService
  └─ 现有 Qwen/DeepSeek 等生成型模型

TypeSafeDecisionService
  └─ Jev Choice / Score / Noul 调用

S2/S3
  └─ 通过统一内部数据结构消费两类模型的结果
```

### 6.2 不用 Jev 生成 MDT 意见卡

意见卡需要事实、推断、鉴别方向、检查建议、信息缺口和质询问题。Jev 不适合生成这些自然语言内容，应继续使用生成模型或模板。

### 6.3 不用 Jev 单独决定急症处置

Jev 仍处于 early access，且中文医疗输入的可靠性尚未由项目验证。急症拦截必须保留确定性规则、人工审核和失败降级。

### 6.4 不使用 `jev-latest` 进行正式评测

`jev-latest` 会随着官方发布移动。评测和阈值校准应固定使用 `jev-1.13.0`，并把响应里的实际版本写入审计日志。

## 7. 推荐的技术架构

### 7.1 新增服务边界

建议新增：

```text
backend/services/typesafe_decision_service.py
```

职责：

- 从环境变量读取 `TYPESAFE_API_KEY`；
- 从环境变量读取 `TYPESAFE_API_URL`，默认 `https://api.typesafe.ai/v1/systemone`；
- 从环境变量读取 `TYPESAFE_MODEL`，默认固定为 `jev-1.13.0`；
- 发送 `state` 和结构化 `questions`；
- 处理超时、429、连接错误和服务端错误；
- 返回统一内部结果；
- 记录模型版本、请求耗时、问题数量、token 使用和错误码；
- 不记录未经脱敏的病例原文。

### 7.2 建议的内部返回结构

```python
{
    "ok": True,
    "provider": "typesafe",
    "model": "jev-1.13.0",
    "answers": {
        "needs_hematology": {
            "type": "noul",
            "noul": 0.82,
        },
        "review_level": {
            "type": "choice",
            "choice": "doctor_review",
            "confidence": 0.91,
            "probabilities": {
                "auto": 0.08,
                "doctor_review": 0.91,
                "block": 0.01,
            },
        },
    },
    "usage": {},
    "latency_ms": 180,
    "error_code": "",
}
```

内部结构不应直接暴露给患者端。最终报告仍使用现有的安全清理和医生审核机制。

### 7.3 配置建议

```dotenv
# Jev 决策服务，独立于现有生成模型配置
TYPESAFE_API_KEY=
TYPESAFE_API_URL=https://api.typesafe.ai/v1/systemone
TYPESAFE_MODEL=jev-1.13.0
TYPESAFE_CONNECT_TIMEOUT=5
TYPESAFE_READ_TIMEOUT=30
TYPESAFE_MAX_RETRIES=2
TYPESAFE_ENABLED=false
```

默认应关闭，先通过离线评测或显式开关启用。

## 8. 数据与隐私边界

当前系统处理医疗病例，Jev 接入前必须先明确数据边界。

TypeSafe 官方隐私资料显示：

- API 输入会被收集和处理；
- 服务托管和处理可能在美国进行；
- 官方说明不会使用客户输入训练模型；
- 企业级数据处理和零数据保留需要结合合同和具体方案确认。

参考：[隐私政策](https://typesafe.ai/legal/privacy-policy)、[数据处理协议](https://typesafe.ai/legal/data-processing)。

在项目当前阶段应执行：

1. 竞赛和演示只使用合成或充分脱敏病例；
2. 姓名、身份证、手机号、住院号、地址等字段不得发送；
3. Jev 请求必须经过现有隐私脱敏层；
4. 记录发送字段和供应商，不记录原始病例全文；
5. 生产使用前确认数据跨境、保存期限、DPA、ZDR 和医疗数据处理要求；
6. Jev 不可用时，系统必须继续使用规则和现有模型 fallback。

## 9. 离线验证方案

### 9.1 第一阶段：只验证 S2 分诊复核

先不改变线上结果，把 S1 规则候选和病例摘要发送给 Jev，得到结构化判断，结果只落盘到实验输出。

建议输入：

- 脱敏病例摘要；
- S1 命中的科室；
- 每个科室对应的规则证据；
- 必要的患者基本信息；
- 明确的判定问题和选项。

建议输出：

- 是否存在该科室的明确证据；
- 是否疑似由既往史或无关段落误触发；
- 是否需要医生复核；
- Jev 概率和 confidence；
- Jev 的模型版本和延迟。

### 9.2 对照组

至少比较以下路径：

1. 纯规则 S1 + S3；
2. 当前 S1 + 生成模型 S2 + S3；
3. S1 + Jev 复核 + S3；
4. S1 + 生成模型 S2 + Jev 复核 + S3。

### 9.3 必须统计的指标

- Macro 召回；
- Macro 精确；
- F1；
- 全命中数；
- 平均选科数；
- 急症拦截率；
- 规则误报率；
- 长病历误触发修正率；
- 医生审核接受率；
- 低 confidence 样本进入人工审核后的命中率；
- confidence 与实际正确率的校准关系；
- P50/P95 延迟；
- 每病例输入 token 和估算成本；
- 服务错误、超时、429 和 fallback 比例。

指标必须按以下子集分别统计：

- 真实 MDT 记录；
- 规格书固定用例；
- 自建用例；
- 急症用例；
- 短病例与长病例；
- 明确阳性、否定表达和信息缺失病例。

### 9.4 初步上线门槛

在没有达到以下条件前，不进入线上默认路径：

- 急症拦截率不低于当前规则路径；
- 分诊召回不低于当前完整链路；
- 精确率没有明显下降；
- 长病历误报率出现可重复改善；
- 低 confidence 样本能够有效导向人工审核；
- Jev 服务失败时现有 fallback 全部通过；
- 中文样本结果经过人工复核；
- 脱敏、审计和数据处理边界得到确认。

## 10. 分阶段落地计划

### Phase 0：接口和数据准备

- 建立 Jev 独立配置项；
- 创建 `TypeSafeDecisionService`；
- 固定 `jev-1.13.0`；
- 实现错误码、超时、429 和 fallback；
- 确认脱敏后的 state 格式；
- 不接入线上主路径。

### Phase 1：离线候选科室复核

- 使用现有评测集跑 Jev；
- 对比规则、当前模型和 Jev；
- 记录各问题类型的概率与实际正确率；
- 人工复核失败案例；
- 重点观察中文、否定、既往史和长病历。

### Phase 2：影子模式

- 线上请求同时调用 Jev，但不影响患者看到的结果；
- 记录 Jev 与现有路径的分歧；
- 统计延迟、失败率、成本和审核意见；
- 只有在服务失败时允许完全静默降级。

### Phase 3：小范围灰度

- 只用于低风险的规则命中复核；
- 不允许 Jev 单独改变急症结果；
- 所有低 confidence 和分歧结果进入人工审核；
- 观察一段稳定样本后再重新校准阈值。

### Phase 4：是否扩大范围

只有当 Phase 1–3 的结果稳定优于现有路径，才考虑扩大到：

- 医生审核分流；
- 意见卡质量检查；
- 信息缺口和追问优先级判断。

## 11. 最终建议

### 推荐做

- 把 Jev 作为独立的结构化决策服务接入；
- 优先验证规则命中复核和候选科室判断；
- 让代码继续掌握阈值、排序、急症规则、冲突和最终审核边界；
- 固定模型版本并记录实际模型版本；
- 用现有 34 例评测集和真实 MDT 子集做 A/B；
- 充分脱敏后再发送数据；
- 先影子运行，再小范围灰度。

### 暂不推荐做

- 直接替换当前 `AIService`；
- 用 Jev 生成 MDT 意见卡；
- 用 Jev 生成患者解释文本；
- 让 Jev 单独决定急诊或高风险处置；
- 直接把官方“结构化、低延迟、低成本”宣传转化为医疗可靠性结论；
- 在未验证中文医疗样本前使用线上默认路径。

## 12. 结论

Jev 与当前系统的“规则优先、模型受限、确定性编排”方向是相容的，最有价值的结合点不是替换现有大模型，而是增加一个低延迟的结构化判断层：

```text
生成模型：理解、解释、意见卡和患者可读文本

Jev：有限选项判断、规则复核、审核分流和输出校验

确定性代码：急症硬规则、阈值、排序、冲突处理和最终安全边界
```

因此，当前建议为：**先做独立适配器和离线 A/B 验证，验证通过后再以影子模式接入；不直接改动现有主链路。**
