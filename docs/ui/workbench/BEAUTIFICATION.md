# 医序工作台美化方案

日期：2026-10-09。范围：登录后的患者与医生界面。此文记录建议和隔离浏览器中的视觉预览。

对比入口：[工作台美化预览](../../../../output/playwright/workbench-ui-plan.html)。可切换 8 个现有视图及桌面、手机截图。

## 当前观察与设计方向

已确认的界面事实：工作台沿用暖白、中性色和陶土色；CSS 中的工作台标题仍使用衬线字体栈。患者有四阶段流程，医生病例处理有五步主流程。此次用合成病例查看了 1440px 与 390px 下的患者录入、病历列表、医生队列、摘要、资料包、分流、MDT 和报告审核，共 16 个视图；未发现页面级横向溢出或 JavaScript 页面错误。

手机医生队列的文字挤窄值得优先处理：当前在 1100px 以下使用两列布局，每个单元内部又为标签预留 5.5rem。390px 时，主诉单元宽约 133px，其中标签占 88px，加上间距后内容空间很少，出现近似竖排的阅读效果。可见，只有“无横向溢出”不足以证明响应式布局可用。

设计建议：延续已确认主页、登录页的暖白、墨黑、陶土色及无衬线标题。工作台通过文字层级、对齐、留白和控件状态建立风格，让资料和操作成为视觉重点。以下对“更清楚”“更协调”的判断属于设计建议，仍需要实际使用反馈。

## 按界面完善

| 界面 | 观察 | 建议 |
|---|---|---|
| 患者填写资料 | 手机顶部导航、病历操作和三种录入方式占据较多纵向空间 | 四阶段改为紧凑且完整可读的导航；新增和我的病历并排；录入方式使用一条分段选择栏；标签清楚、输入区留足空间，继续按钮形成唯一当前主操作 |
| 患者病历列表 | 病例号、状态、主诉和操作集中在相似的小卡片中 | 主诉或本次诉求优先；病例号和日期放入元信息；统一打开病例与查看历史的主次关系；以分隔线和组间距减少重复边框 |
| 医生病例队列 | 手机单元被标签和两列结构挤窄；统计区和详情区重复使用带底色的小容器 | 桌面保留五列病例表格；手机改为主诉驱动的列表条目，风险和状态并排，更新时间单独成行；统计整理成简洁摘要，完整保留现有筛选与风险信息 |
| 病例摘要 | 标题和正文风格与新登录页存在差异；结构化事实有较多小块边界 | 使用统一的无衬线标题；主诉、已知事实、信息缺口各成分区；来源紧随对应事实，可展开的原文入口保持明确 |
| AI 资料包 | 页面卡片内仍有资料包外框、专科卡片和内部背景块 | 减少外层重复边框，通过专科标题、内容组和留白区分；保留当前事实、AI 判断、待医生判断和缺口的分区；来源及“AI 参考”标识保持可见 |
| 分流确认 | 方向选择、科室、参与范围和目标需要一起理解 | 处理方向先显示为清楚的选择组，下方填写对应科室和目标；手机标签与控件分行，选中状态同时用文字和形状表示；继续沿用现有一次确认流程 |
| MDT 协作与会诊记录 | AI 讨论参考与正式医生记录属于不同内容；当前预览病例尚未完成分流 | 顺序呈现确认范围、AI 参考、分歧及正式记录；已有医生记录使用明确标题和编辑区；生成中、失败、过期分别给出可执行提示，正式内容保留原有保存与发布规则 |
| 报告审核 | 审核分类、统计、前置条件和最终建议同屏；多个按钮视觉权重相似 | 分类查看使用次级按钮；发布前条件形成一份清楚的待办清单；最终建议与患者报告预览形成主区域；按既有规则完成审核、预览及确认发布 |

患者医生结果页与历史报告作为后一批补充：顶端明确是否已发布、医生身份、发布时间和版本；依次展示最终建议、下一步安排及待补资料。报告正文采用稳定的阅读版式，历史版本形成时间线，完整来源与打印报告继续可查。方案阶段未采集发布后的患者报告，实施阶段已通过合成发布流程核对这些状态。

## 统一视觉与控件规则

- 配色复用已有 token：暖白 `#faf9f5`、白色 `#fff`、墨黑 `#141413`、陶土色 `#a94f35`。墨黑用于当前主操作，陶土色用于文字入口及小范围强调。风险与状态色继续配明确文字。
- 工作台标题采用现有中文无衬线栈，页面标题建议桌面 28px / 手机 24px，分区标题 18px，正文 15–16px，说明 13–14px。病例号保留便于识别的格式，避免靠缩小文字适应布局。
- 页面、分区间距建议 24–32px，相关字段间距 8–12px；输入和主按钮使用轻圆角。外层容器保持一种边界，内部尽量依靠分区标题与细线组织。
- 手机按钮及输入目标建议至少 44px 高。原生 checkbox 本体可较小，但必须核对整个可点击标签范围，不能仅凭 checkbox 的尺寸判断是否可用。
- 当前提交、继续或预览动作使用主按钮；返回、查看、筛选和辅助操作使用次级样式。保留现有禁用、请求中、错误和成功反馈。
- 空病历、空队列、未生成、部分失败及过期状态采用一条明确说明和可执行操作；展示数据以真实状态为准。
- 列表选中、阶段切换可使用约 150–220ms 的轻量反馈。内容默认可见；减少动态效果时保留选中反馈，关闭位移。长报告、正式记录输入及风险内容保持稳定。

## 实施顺序与验收

1. **第一批：公共组件、患者录入、医生队列。** 先处理手机布局和文字可读性，统一标题、按钮、输入和焦点样式。检查录入切换、列表打开、筛选、详情展开及 Tab 顺序。
2. **第二批：病例列表、摘要、AI 资料包与分流。** 调整分区、元信息、来源及主次操作；保留当前资料与科室确认逻辑。
3. **第三批：MDT、报告审核、患者结果与历史。** 补齐真实内容和所有状态，核对编辑内容、版本、权限、预览和发布动作。打印版式单独验收。

落地时复用现有 HTML、CSS、JavaScript 与 token，在工作台范围内定义覆盖，控制公共样式对首页、登录页和打印页的影响。现有流程、权限、风险信息、医生确认和报告版本规则继续作为验收依据。

响应式验收需要覆盖 1440、1280、1024、960、768、390、320px，并检查内容单元的实际宽度、当前阶段是否可见、触摸范围、长文本换行及浏览器缩放。不能仅检查 document.scrollWidth。同步核验正文与占位符对比度、键盘焦点和减少动态效果。

## 预览证据与边界

预览通过浏览器注入独立 CSS，患者录入预览另调整标题和一行引导。没有写入产品模板、共享样式或业务逻辑。所有病例来自内存 SQLite 与合成账号，外部 AI 调用关闭。

截图覆盖上述 8 个视图的 1440px / 390px。MDT 展示的是分流未完成状态，生成中、失败、过期与正式编辑仍需在实施中补齐；本次也未验证发布后的患者报告、完整打印或所有长文本情况。预览检查不替代业务流程回归及完整可访问性验收。

浏览器原始观察和预览检查分别保存在 `output/playwright/workbench-plan-observations.json`、`workbench-plan-proposal-checks.json`；预览 CSS 为 `workbench-plan-preview.css`。这些路径相对于工作区 `E:/aic_competition`，不作为生产依赖。
