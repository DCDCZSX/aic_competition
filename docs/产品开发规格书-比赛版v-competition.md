## 1. 行为类型总表（合并 v1.0 三套分类，评审 v1.0 §1.1 修复）

全系统只有**一套**行为类型，`用户目标 → 行为类型(A-E) → 触发信号 → 输出模板` 一张表贯穿（录入/分诊/Guardrail/报告共用）：

| 类型 | 用户目标（主文档 §5.1） | 触发信号（S1 判定） | 输出模板 |
|---|---|---|---|
| A 单科简单 | 不知道挂哪个科（单系统、无共病） | 单系统、无共病、无手术/危象词 | 单科就诊建议 + "为何不需 MDT"一句 |
| B 多病共病 | 多病共存想整理复杂情况 | 已确诊慢性病 ≥2 且跨系统症状 | MDT：临床科牵头 |
| C 疑难排查 | 疑难复杂病例备 MDT 材料 | 血象异常/发热查因/诊断不明/多系统受累 | MDT 多科排查 |
| D 手术/介入决策 | 手术/介入前整理问题 | 术式/介入/围术期决策词 | MDT：外科牵头 + 麻醉/影像/内科评估 |
| E 危象/不可用 | （不来自目标，S1 直判） | §4.1 危象词表命中；非医学/空输入 | **拒绝出报告**，转 120/急诊或礼貌拒绝 |

> 三类修正点（对应评审意见）：① 目标 C"整理多个医生意见"不单独成类型，作为 **B/C/D 上的增强模式**（意见对比展示开关），避免第五类行为；② E 不来自目标选择，由 S1 规则直判（单一触发器见 §4）；③ 患者可改目标，但目标只调展示与追问策略，不直接决定分诊。

## 2. P0 演示核心链路（比赛视频主线，评审 v2.0 §1.1 修复）

```
就医目标(轻量,可跳过) ─▶ 粘贴录入 ─▶ 脱敏预览与来源标注 ─▶ 【提交】画像确认(门禁)
   ─▶ 追问(≤1轮≤3问) ─▶ 分诊(S1→S2→S3) ─▶ 就医路径+Action Center
   ─▶ AI 多学科分析(3-4科) ─▶ 聚合 ─▶ 一页摘要+完整报告
   ─▶ (演示)就诊后: 患者补资料 → 医生端录线下意见 ─▶ 变化摘要/对照

执行形态（2026-09-14 落地，见 §6.0）：
  点【确认脱敏并提交】后 → **35-200 ms 先出规则结果**（画像/追问/规则分诊/路径）
  模型三相在后台继续：画像增强 → S2 发言+重编排 → 多学科意见卡+质询（实测 16.7 秒）
  结果到达即**自动替换**前台内容；进度可在右轨与 P8 实时看到，失败可一键重试
```

每步演示验收（录屏/答辩对照）：

| 步骤 | 观众看到什么 | 演示口播点 |
|---|---|---|
| 就医目标(轻量) | 1 个主选项 + 可折叠"更复杂情况"，可跳过 | 面向中老年，只讲人话、无术语；目标只调策略不改分诊 |
| 粘贴录入 | 粘贴一段出院小结 + 主要问题 | 支持双 Tab（粘贴/表单），表单含既往史快捷点选 |
| 脱敏预览 | PII 自动打码预览 | 隐私合规实拍 |
| 画像确认 | 分组画像卡 + source_ref 悬停 + 信息缺口 | **"先对齐事实再分析"第一道闸** |
| 追问 ≤1 轮 | 高价值问题 ≤3 个（带"为什么问/可跳过"） | 追问由依赖矩阵驱动（§7.2） |
| 分诊 | 牵头科 + 协同科 + 理由 + 可靠性等级 | S1 规则命中的信号文本可展开 |
| 路径 + Action Center | 条件分支路径 + 任务清单 | **把建议变成任务（产品气质升级点）** |
| AI 多学科分析 | 患者端：各科摘要卡；医生端：逐科审阅（屏 E） | 过程归医生端（患者只关心结论与下一步） |
| 聚合 | 共识 / 分歧 / 不确定性（医生端工作台） | 分歧如实呈现 + 建议线下复核 |
| 报告 | 一页摘要 + 医生审核版完整报告 | 打印为 PDF |
| 就诊后回流 → 变化摘要 | 患者补充新资料 → 医生端录入线下实际意见 → 只重算受影响模块 → "这次新资料改变了什么" | **AI vs 医生对照 + 增量更新闭环** |

## 3. 医生端比赛版定位（评审 v1.0 §1.3 / v2.0 §1.2 修复——叙事负债解法）

### 3.1 结论
- **主闭环 = 患者端全流程 + 就诊后回流对照**（患者补充新资料 → 医生端/医院录入线下实际意见 → AI vs 医生对照，见主文档 §14）。
- **登录与角色（衔接主文档 §11）**：比赛版提供**预置演示账号 + 角色分流入口**（`patient_demo` / `doctor_demo`，或"进入患者演示 / 进入医生演示"按钮），登录页只做角色识别与本地会话，**不引入真实注册/认证体系**（短信、实名、医院统一认证 = P2）。这满足"软件产品完整性"叙事，同时不增加真实账号复杂度。
- **医生端 = 演示级只读审核台**：接受 / 修改 / 驳回 / 暂不确定 + 记录落库（SQLite），UI 完整但**单机演示、单账号**。
- **验证方案（文档明写，防答辩穿帮）**：队伍接触不到真实医生，采用 **1-2 位医学背景同学扮演审核人做概念验证**，材料中标注"医生端为概念演示，真实临床验证属后续计划"。

### 3.2 医生端范围（比赛版）
| 功能 | 比赛版动作 |
|---|---|
| 病例列表 / 总览 | ✅ 只读，从本地库读 |
| 分诊依据 / 证据板 | ✅ 只读展示 |
| AI 专科视角审阅 / 共识分歧工作台 | ✅ 只读（屏 E MDT 会诊审阅台，含"播放逐科分析"） |
| 接受 / 修改 / 驳回 / 暂不确定 | ✅ 记录入 `doctor_decisions` 表 |
| 补资料请求 | ✅ 生成一条"补充就诊后资料"任务给患者侧（走 §7 回路） |
| 录入线下实际意见 | ✅ 就诊后由审核人录入真实医生意见 → 生成 AI vs 医生对照（屏 F，比赛版演示用） |
| 身份认证 / 授权 / 审计 / 多用户 | ❌ P2（比赛版用预置演示账号 + 操作日志即可） |

### 3.3 演示合规细节（补回 v1.0 §20.2）
- 任何**未过医生确认**的报告/页面固定标注：**"AI 生成，尚未经医生审核"**（含演示模式的导出件）。
- 医生确认后版本才标"审核版报告"，并在报告中列出审核人与时间。

## 4. Guardrail 与科室域（评审 v1.0 §2.2 / v2.0 §2 修复：单一触发器 + 域定义）

### 4.1 危象拦截（全系统唯一危象触发器，E 型引用它）
- 词表集中维护（`guardrail_crisis_rules.py`，内置 ≥40 条，附审计清单：词→理由→来源）。
- 组合规则示例：`胸痛 + 大汗`；`意识障碍 + 突发`；`严重呼吸困难`；`大出血`；`板状腹`；`自杀/伤人`；`药物过量/中毒`；`持续高热 + 抽搐` 等。
- 触发动作（G1，见 §4.4）：阻断分诊与 MDT → 显示"疑似急症，请立即拨打 120 或前往急诊" → 不生成任何分析/报告 → 记录触发依据。

### 4.2 科室域 v1（唯一权威源 = 代码字典 `SPECIALISTS`）
- 归类原则：① 以"能独立对 MDT 议题给出意见的临床单元"为粒度；② 亚专科并组；③ 辅助诊断科可参与但**不得牵头**；④ 牵头仅限临床科，`primary_department` 由临床科担任；⑤ 高频独立科（超声科、肝胆外科、介入科）单列。
- 全集（37 门类）：
  - 临床内科(13)：心血管内科、神经内科、呼吸内科、消化内科、肾内科、内分泌科、血液科、风湿免疫科、感染科、肿瘤科、老年医学科、急诊科、重症医学科
  - 外科系(8)：普通外科、肝胆外科、骨科、神经外科、心胸外科、泌尿外科、血管外科、整形外科
  - 临床专科(10)：皮肤科、眼科、耳鼻喉科、精神科、康复医学科、妇产科、儿科、新生儿科、中医科、针灸科
  - 辅助科(6)：影像科、超声科、病理科、检验科、介入科、麻醉科
- 别名映射 `ALIAS_MAP`（评测与分诊共用）：心内科→心血管内科；呼吸科→呼吸内科；肾内→肾内科；血液内科→血液科；感染性疾病科→感染科；风湿科→风湿免疫科；康复科→康复医学科；耳鼻咽喉科→耳鼻喉科；神外→神经外科；ICU→重症医学科 …（完整表随字典维护）。
- OOV（域外科，不静默丢弃）：① 命中 `ALIAS_MAP` → ② 命中"最近似科表"并提示"已按近似科 XX 处理" → ③ 记 `oov_log`，报告中原样呈现"建议咨询 XX（未建模）"。
- 评测口径分两列报告：域内指标 / 含 OOV 近似指标（诚实）。

### 4.3 决策链（S1 规则 → S2 模型 → S3 安全约束与决策编排）
- **S1 规则引擎（确定性）**：规则=(条件,科室,权重,触发信号)，strong=3/medium=2/weak=1；行为 A-E 由 S1 判定；E 不进 S2。输出每科 `score_R` + 命中信号文本（可解释）。
- **S2 模型层（受限发言）**：上下文含画像 + 主要问题 + 科室域 + S1 清单及理由；指令"逐科说明采纳/补充/反驳，反驳强规则必须给医学依据；只对自己新增的科自报 0-1 置信度"。**模型无权移除 strong 命中。**
  - **第一轮独立研判（防锚定，主文档 §8.1 落地）**：各专科视角在汇聚前**互不预读彼此结论**，只基于画像+本专科任务独立输出；分歧识别（§6.3 质询触发）在全部独立结果就绪后才进行。
- **S3 安全约束与决策编排（确定性，无模型参与）**——只做编排不裁定医学真相：
  - strong 命中 → 必选；medium/weak → 入选（weak 标"可咨询"优先级）；仅 M 新增 → `conf ≥ 0.65` 且过校验器才入选；
  - 校验器：科室∈域表；总数 ≤6；D 型强制外科牵头 + 麻醉/影像之一；牵头位=临床科；
  - 冲突不静默：M 反驳 strong → 保留该科 + 记 `conflict_log` → 分歧区呈现；
  - 每病例记 `decision_path ∈ {rule-dominant, model-dominant, mixed, refused, degraded}`。
- 打分口径：只保留规则权重分(S1)/模型置信(S2)/校验布尔(S3)，**任何分数不出现在用户可见 UI**；用户只见理由与优先级标签（主文档 §2.5）。

### 4.4 拒绝与降级表（G1-G6，唯一声明点）

| ID | 触发 | 动作 |
|---|---|---|
| G1 | 危象词表命中（§4.1，≥40 条） | 阻断：提示 120/急诊，不进会诊不出报告，记触发依据 |
| G2 | 主诉与主要问题双空 | 阻断，引导补录 |
| G3 | 输入命中 PII（18 位身份证/11 位手机号等） | 阻断并提示清除（不分析），展示脱敏预览 |
| G4 | 画像校验失败：主诉未抽取 或 原文直引覆盖率 <0.60 | 阻断回画像确认，提示补录/改表单 |
| G5 | 模型连续 3 次失败 且 规则零命中 | 降级：输出固定就医建议模板，不生成 AI 报告（见 §8） |
| G6 | 非医学内容（闲聊/广告/试题） | 礼貌拒绝并说明用途 |

## 5. 数据结构 schema（评审 v1.0 §2.3 / v2.0 §2 修复：类型/枚举/JSON 样例）

> 通用约定：`confidence ∈ {high, medium, low}`；`state` 枚举见各表；所有"判断"须带 `source_refs[]` 与 `evidence_state`；schema 校验失败即降级/阻断（G4/G5）。键名三列表随本文附录 A 维护，代码与文档以 `schemas.py` 为唯一权威源。

### 5.1 PatientProfile（画像）
```json
{
  "case_id": "C001",
  "behavior_type": "B",
  "portrait": {
    "age": 58, "sex": "女",
    "chief_complaint": "视物模糊3月，下肢浮肿1周",
    "diseases": [{"name": "2型糖尿病", "duration": "5年", "control": "不详",
                  "confidence": "medium", "source_refs": ["S-2:12"]}],
    "symptoms_timeline": [{"symptom": "视物模糊", "onset": "3月前", "trend": "渐重",
                           "confidence": "high", "source_refs": ["S-2:12"]}],
    "exams": [{"item": "尿蛋白", "value": "++", "abnormal": true, "source_refs": ["S-1:34"]}],
    "medications": [{"name": "二甲双胍", "dose": "0.5g bid"}],
    "doctor_opinions": [],
    "information_gaps": ["血糖控制水平不详", "未提供眼底检查"]
  },
  "completeness": 0.72,
  "direct_quote_coverage": 0.65
}
```
- 关键字段 = {主诉, 症状时间线端点, 关键异常检查, 当前用药, 主要问题}；`completeness` = 关键字段集合填充率。
- **画像门槛（评审 v2.0 §2.1 修复）**：`completeness ≥ 0.6` 放行（缺口随行标注）；`direct_quote_coverage ≥ 0.60`（G4）；high 缺口（依赖矩阵中影响 ≥1 专科判断的字段缺失）→ 阻断追问 ≤1 轮后仍缺 → 放行但可靠性等级降一级。

### 5.2 TriageResult（分诊）
```json
{
  "case_id": "C001",
  "behavior_type": "B",
  "primary_department": {"code": "endo", "name": "内分泌科", "role": "牵头",
                          "reason": "糖尿病5年血糖控制不详，为多病基础病", "signals": ["规则:糖尿病→内分泌(strong)"]},
  "secondary_departments": [
    {"code": "neph", "name": "肾内科", "reason": "蛋白尿需评估糖尿病肾病"},
    {"code": "oph", "name": "眼科", "reason": "视物模糊需眼底检查"}
  ],
  "reliability": {"level": "中", "reasons": ["血糖控制情况缺失"]},
  "needs_doctor_review": true,

```
- 入选规则见 §4.3；`reliability` 由 §5.7 综合：证据来源可靠度/关键字段完整度/规则支持/多模块一致/冲突/医生确认 → 高/中/低 + 原因。

### 5.4 MDTAggregation（共识/分歧/不确定性聚合）
```json
{
  "consensus": [{"topic": "需优先完善血糖评估", "supporters": ["内分泌科","肾内科"]}],
  "disagreements": [{
      "topic": "是否首选有创性血管评估",
      "positions": {"心血管内科": "建议冠脉CTA", "肾内科": "先控制蛋白尿再评估"},
      "reason": "证据时间不同/专科优先级差异",
      "resolving_info": "血糖控制水平与肾功结果",
      "evidence_state": "conflict"
  }],
  "uncertainties": [{"topic": "血糖长期控制水平", "impact": ["全部三个专科判断"]}]
}
```
- **分歧检测 v0（评审 v2.0 §3.3 修复）**：只对"双高相关科室"做方向性比对——用 `opinion/checks` 反义词表（如"建议手术↔保守观察""立即↔暂缓""首选A↔首选B"）+ LLM 复核；验收线：精确率 ≥0.70，宁少勿多（§8）。
- 不做语义级全量检测；同科不一致不算分歧；记录 `resolving_info`（哪项新信息可解决）。

### 5.5 TaskItem（Action Center，评审 v2.0 §3.1 修复）
```json
{
  "task_id": "T-001", "case_id": "C001",
  "type": "就医咨询任务",
  "content": "向内分泌科医生确认：当前血糖控制目标与是否需要调整二甲双胍剂量",
  "source": "endo:checks[high]",
  "priority": "high",
  "depends_on": ["T-000"],
  "state": "todo",
  "created_at": "…", "completed_at": null
}
```
- 类型枚举：`资料准备 | 就医咨询 | 就诊后资料更新`；来源规则 = 分诊路径步骤 ∪ 各科 high checks ∪ 医生补资料请求。其中"就诊后资料更新"在患者侧 = 上传新检查/新方案/症状变化；医生侧 = 录入线下实际意见（走 §7 回路）。
- **任务状态机**：`todo → doing → done（触发局部重算→变化摘要）`，`todo → cancelled`（依赖变化取消），`done → reopened`（新资料使结论变化，走 §11）。
- 医疗行为类任务只允许文本"建议向医生确认是否需要××"，禁止指令式。
- **补充说明**：患者侧任务只负责"提交手上有的资料"，不要求患者替医生写意见；医生意见以 `doctor_decisions`（录入线下意见）或医院系统对接为准。

### 5.6 DoctorDecision（医生审核记录，评审 v1.0 §2.4 修复）
- **审核单位 = 决策条目**：`科室入选 / 路径步骤 / 共识分歧条 / 患者建议`，每条一状态。
```json
{
  "decision_id": "DD-001", "case_id": "C001",
  "target_type": "department_selection",
  "target_id": "oph",
  "action": "accept",
  "before": null, "after": null,
  "reason": "同意先做眼底检查",
  "reviewer": {"role": "演示审核人-医学生", "dept": "眼科"},
  "evidence_refs": ["exam:眼底检查-缺失"],
  "version": 3,
  "created_at": "…"
}
```
- `action ∈ {accept, modify, reject, uncertain, supplement_opinion, request_more_info}`。
- 资料更新 → 受影响区重算 → `version+1` → 受影响条目回 `pending`（保留医生原意见为对比，主文档 §10.2）。

### 5.7 ReliabilityLevel 综合规则（主文档 §6.5 落地）
`reliability = f(证据来源可信度, 关键字段完整度(§5.1), 规则支持度, 多模块一致性, 冲突数, 医生确认状态)`：
- 高：关键字段全、冲突少、证据直接；中：有缺口或间接证据；低：资料不足/冲突/纯推断。
- **模型自报置信度只进 S3 决策，不进可靠性等级**（主文档 §2.5 红线）。每个等级必须附原因列表。

## 6. 依赖矩阵与增量更新（评审 v2.0 §3.2 / 主文档 §13 落地）

### 6.0 分析任务的执行形态：渐进式 + 按需 + 可重试（2026-09-14 落地）

> 动机：建模链路一次要点 3 次模型（画像增强 / S2 受限发言 / 多学科意见卡 + 质询），实测 **29.8 秒**。
> 患者点"确认脱敏并提交"后干等半分钟，会以为卡死。所以把"模型参与的部分"从主请求里剥离。

| 机制 | 规则（写死） |
|---|---|
| **渐进式首屏** | `POST /api/v2/case {progressive:true}` 只跑**确定性规则**（画像抽取 / 追问 / S1+S3 规则分诊 / 路径），实测 **35–200 ms** 返回；模型三相随后后台跑并**自动替换**前台结果 |
| **后台三相** | `profile`（画像模型增强）→ `triage`（S2 受限发言 + 重新编排 + 重新生成路径）→ `mdt`（多学科意见卡 + 质询）；每相独立成败，**单相失败不连坐** |
| **进度可查** | `GET /api/v2/case/<id>/analysis`：三相状态 + MDT 细分进度（第几科 / 当前子步骤）+ 已就绪结果片段 + 警告；进度**落库**（刷新页面不丢） |
| **两段式（兼容）** | `defer_mdt:true` = 画像/追问/分诊/路径同步（约 3 秒）、仅 MDT 后台；给需要确定性时序的场景（医生端批处理、测试） |
| **按需跳过 MDT** | 就医方向只有 **1 个**科室时不跑多学科会诊，如实标注 `mdt.state="skipped"`（"仅 1 个就医方向，无需多学科会诊"），**不假装分析过** |
| **结构化输出预算** | 结构化输出（多学科意见卡等）**必须**调大 `max_tokens` 并检查 `finish_reason`：实测血液科意见卡需 ~2335 token，默认 2000 会把它截断成非法 JSON → 整科被丢弃。意见卡预算 4000；被截断时先按"更精炼"要求重试一次，仍不行则按**已写出的字段**容错恢复并如实标注 |
| **降级可见** | 模型不可用时相位仍收尾，但必须把原因写进 `analysis.warnings` 并在界面展示（"模型增强失败，已回退为规则抽取"/"S2 受限发言未生效"/"以下专科分析未完成"）；**逐科失败不得对外显示"全部完成"** |
| **逐科失败可见且可重试** | MDT 里某个科室没跑出来 → `analysis.mdt.failed=[科室]`、`phases.mdt.state="partial"`（有科室成功）或 `"failed"`（一个都没成功）、病例 `analysis.state="partial_failed"`，**其余科室结果照常可用**；重跑该相位会先清掉这些科室的旧告警 |
| **失败可重试** | 相位抛未捕获异常 → `state=failed` + `note`（`异常类型: 消息`）；`POST /api/v2/case/<id>/analysis/retry` **只重跑未完成/部分完成的相位**（含"相位算完成但有科室失败"，以及修复前就卡住、没有分析记录的老病例）；全部完成时返回 400 并说明"无需重试" |
| **医生端批处理** | `POST /api/v2/cases/analyze {limit}` 把"分析未完成（含个别科室未完成）"的病例排队进后台（已在跑/已完成进 `skipped`，不重复排队）；`running` 超过 10 分钟视为线程已丢失、允许重排；列表每行带 `analysis_state`（分析中/分析就绪/部分未完成/分析失败/未分析） |
| **状态机联动** | 后台任务启动时病例置 `analyzing`；三相结束后推进到 `awaiting_doctor`（医生端据此当"待审"处理） |

红线不变：规则结果**先于**模型结果呈现；模型只能补充、不得推翻规则命中的强项；降级与失败必须如实说明，**不得用"正在分析"掩盖已失败**。

### 6.1 字段-专科依赖矩阵（v1 手写、规则驱动，20-30 条核心映射）
| 画像字段 | 依赖它的专科/判断 |
|---|---|
| 血糖控制水平 | 内分泌科全部判断、眼科(视网膜评估)、肾内科(肾病分期) |
| 尿蛋白/肾功能 | 肾内科判断、内分泌科(糖尿病肾病)、心血管(容量评估) |
| 眼底检查 | 眼科判断、内分泌科(并发症) |
| 心脏/冠脉检查 | 心血管内科、麻醉科(D型)、心胸外科 |
| 术式/介入词 | S1 D 型判定、外科牵头科、麻醉科/影像科参会 |
| 用药清单 | 所有专科(相互作用)、分诊路径(停药/换药建议) |

- **追问高价值定义**：缺失字段 ∈ 依赖矩阵中影响 ≥1 个专科判断的字段（一套机制两处受益：追问 + 信息影响分析）。
- 增量更新影响范围 = 查矩阵 → 只重跑受影响模块 → `version+1` → 生成变化摘要（§5.6 回审）。

### 6.2 Evidence Board 比赛版范围（主文档 §9 + 功能深化方向 §五）
只做三块：① 时间线；② 判断↔证据关联（每条判断点开看支撑资料/反向证据/evidence_state）；③ **分诊级 what-if**：补一个字段 → 只重算分诊，不重算整个 MDT。全量会诊级 what-if = P1。
- `evidence_state ∈ {direct, indirect, missing, conflict, doctor_confirmed, awaiting_doctor}`；**"相关"不等于"支持"**，仅同源直引才标 direct。
- **证据卡片双列（主文档 §9.4 落地，P0 简化版）**：判断卡展开 = 支持证据列 + 反对证据列；患者证据挂 source_ref，外部医学证据仅做"可追溯来源条目"（教材/公开指南），**比赛版不接 RAG/向量检索**——外部证据条目由规则表/人工维护的少量白名单提供，命中才显示，未命中显示"暂无可靠外部依据"，杜绝伪造文献。质询标记（已质询·需补××）随 DoctorDecision 记录落库。

### 6.3 交叉质询与第二轮（主文档 §8.4 落地，比赛版取舍）
- **P0（轻量，嵌入现有 MDT 编排，不新增独立 Agent 常驻）**：当聚合输出检测到"双高相关科室分歧"或"与外部规则冲突"时，编排器自动追加**一轮质询**——由牵头专科视角生成 ≤3 条挑战问题，相关专科各补答一次"补充证据/修正观点/维持并说明理由"，结果并入分歧区与报告。
- **P1（完整质询体验）**：独立 Challenge 视角常驻、跨两轮状态机、质询前后对照视图、"诊断锚定"专项检查。
- **红线（写死）**：任何质询结果**不得输出概率数字或"置信度变化"**；第二轮的变化以"分歧是否被质疑 / 哪些判断需补充证据 / 哪些需医生裁决"呈现（主文档 §8.4）。
- 参考演示案例：内分泌牵头 + 肾内/眼科的共病病例中，质询点天然出现在"眼底检查缺失时是否仍建议眼科优先"这类分歧上——比感染性脑病案例更贴近 P0 演示主用例。

## 7. 病例/报告状态机与补资料回路（主文档 §16 落地 + 评审 v2.0 §3.5 修复）

### 7.1 病例/报告状态机（P0 必须实现，状态落库可查）

```
资料待确认 ─▶ AI 分析中 ─▶ AI 分析完成 / 待医生审核
                              ├─▶ 退回补资料 ─▶ （患者补资料/医生录意见）─▶ 待复核
                              └─▶ 医生已审阅 ─▶ 医生已确认
                                                    └─▶ 新资料进入后待复核 ─▶ 回到「AI 分析中」
```
- 状态枚举落库（`case_state` / `report_state`，见 §5 schema），前端顶栏与列表可见（医生端屏 A 的待审计数即由此聚合）。
- **异常处理（主文档 §16 原文要求，写死）**：遇到模型超时、JSON 解析失败、证据无法核验、规则与模型冲突、急症风险不确定时——**显示明确原因 + 保留原有版本 + 转入人工复核或补资料状态**；**不得静默生成空白报告或确定性结论**（与 §8 失败降级表配合）。
- 状态流转必须留痕：每次流转记 `time / actor / reason`，进入屏 G 审计时间线。

### 7.2 补资料回路

```
医生请求补资料/录入线下意见 ─▶ 患者侧生成「就诊后资料更新」任务(T-xxx, state=todo)
   ─▶ 患者上传新资料(来源分级：患者上传/医生上传/医院文档/未验证) ─▶ 校验(G4)
   ─▶ 医生端录入线下实际意见(演示版=审核人) ─▶ 依赖矩阵定受影响模块
   ─▶ 局部重算 ─▶ version+1
   ─▶ 受影响决策条目回 pending(保留医生原意见对比) ─▶ 医生重新确认(演示审核人)
   ─▶ 变化摘要/ AI vs 医生对照 推送给两端
```
- 患者上传内容与"患者转述的医生意见"**永不自动**成为医生确认意见（主文档 §14）；正式医生意见由医生端录入或医院系统对接，AI vs 医生差异在此进入对照视图。

## 8. 失败处理与降级分支（评审 v2.0 §2「丢失件」修复）

| 场景 | 处理 |
|---|---|
| S2 模型连续 3 次失败 且 S1 规则零命中 | G5 降级：固定就医建议模板 + 不生成 AI 报告，状态 `degraded` |
| 单专科分析失败 | 该科标"本次未完成分析"+ 原因；`mdt.failed` 记录，相位记 `partial`/`failed`，**其余科不阻塞**；患者端「重新分析」/医生端「批量补齐分析」可重跑（只重跑失败部分） |
| 单科超时（120s） | 重试 1 次 → 仍失败标"未完成"跳过，报告注明 |
| 全流程总时长 | 上限 8 分钟；内存会话，刷新提示重来（比赛版不做落盘恢复） |
| 模型输出被 `max_tokens` 截断 | 结构化输出统一带足预算（意见卡 4000）并检查 `finish_reason`；被截断 → 按"更精炼"要求重试一次 → 仍截断则按**已写出字段**容错恢复并在卡片上标注"输出被长度截断，已按已写出的字段恢复"（**半个字符串不入库**） |
| JSON 解析失败 | 容错解析 `services/json_recovery.py`：配平提取 → 格式修复（全角标点/未转义引号/裸换行/尾逗号/注释/Python 字面量）→ 逐字段抢救；全失败才按上表降级，且原因如实写明（区分"截断"与"格式异常"） |
| LLM 输出字段缺失 | 字段校验器 → 缺必填字段该条标"不完整"并提示重试 |
| 无效输入 | G2/G6（§4.4） |

## 11. 数据与合规（比赛口径，评审 v1.0 §2.7 / v2.0 §3.6 修复）

| 项 | 比赛版设计 |
|---|---|
| 知情同意 | 首次使用弹窗：①用途=生成就医参考 ②病历文本将发送至第三方大模型 API ③不用于训练 ④可随时删除 |
| 存储 | 本地运行；病历**原文不落盘**（仅内存）；落盘 = 脱敏画像 + 各版本报告 + 审核/审计记录（"档案模式"边界） |
| 保存期限 | 会话记录 ≤30 天自动清理；"一键删除全部数据"同时清档案（含各版本与统计） |
| 脱敏 | 前端提示 + G3 PII 拦截；对外材料只用改写病例，注明"已脱敏、仅用于技术验证" |
| 演示数据 | MDT-5.csv 使用前确认来源授权与脱敏程度；展示时改写原始对话 |
| 能力边界 | 报告固定段"本系统不能做什么"（§9.3 P2 清单 + 急诊/儿科急症/精神危机/处方剂量等） |
| 医生端 | 演示审核人固定身份 + 操作日志；无真实患者数据 |
| 模型/凭据 | API Key 只读环境变量（.env 不入包）；考古报告红线项：旧明文 Key 作废重建 |
