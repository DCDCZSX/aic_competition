## 2. 三条额外事实（比原报告更关键）

### 2.1 `needs_doctor_review` 的语义被抹掉，而不是"只是没参与判断"

```python
review_service.py:207  needs_doctor_review=bool(step.get("requires_doctor"))   # 路径步骤确实标了免审
review_service.py:246  needs_doctor_review=True
review_service.py:296  needs_doctor_review=True
review_service.py:329  item.needs_doctor_review = item.state in (AWAITING, UNCERTAIN)  # ← 整体覆盖
review_service.py:339  "can_publish": total > 0 and pending == 0                       # ← 闸门只看状态
```

- **覆盖**：业务语义（谁是免审的）在构建末尾被"是否还没审"取代；
- **无人读取**：全仓其余同名字段来自另外两个概念（`triage.needs_doctor_review`、`update_service` 的变化摘要），
  `ReviewItem.needs_doctor_review` 既没进 `summarize()`，也没进前端。

**实测规模（库中前 100 例）**：**560 条路径步骤为 `requires_doctor=False`，占全部条目 21.9%**。
按语义实现后，**待审量立刻降约 22%**，且发布不再被这些条目卡住。

### 2.2 负担的主因不是"科室选择"，而是**患者建议 + 路径步骤**

| 条目类型 | 条数 | 占比 |
|---|---|---|
| `patient_advice` | **1075** | **42%** |
| `path_step` | 660 | 26% |
| `consensus_item` | 431 | 17% |
| `department_selection` | 390 | 15% |

→ "异常优先"设计必须先回答**这两类怎么降级**：患者建议本质是"给医生看的信息"，不是"需要裁决的决策"，
它更接近"确认已知悉"而非"逐条裁决"。

### 2.3 队列有两个隐藏上限（做队列主屏前必须解决）

- 左轨 `slice(0,20)`（只显示最近 20 例）；
- 后端 `list_review_cases(limit=100, ...)` —— **超过 100 例会静默截断**，队列主屏必须先分页/虚拟滚动。

## 3. P0 设计：审核状态模型 + 发布闸门

### 3.1 状态模型（在现有 4 态之上补 1 态，并明确"谁的责任"）

| 状态 | 含义 | 谁产生 | 是否计入"待审" | 能否进报告 |
|---|---|---|---|---|
| `auto_processed`（**新增**） | 规则/AI 自动处理（格式、去重、缺字段提示等） | 规则 | 否 | 可以，但**必须标注"自动处理"** |
| `awaiting` | 等待医生裁决（必审） | — | **是** | 未终态不可发布 |
| `confirmed` / `modified` / `rejected` / `uncertain` | 医生已处理（沿用现枚举） | 医生 | 否 | 可以 |
| `doctor_confirmed`（病例级，沿用） | 医生已发布审核版 | 医生 | — | 报告角标转绿 |

### 3.2 发布闸门（替换现在的 `pending == 0`）

```
可发布 =
  所有 needs_doctor_review = true 的条目已到终态
  且 无"未解决的关键冲突"（triage.conflicts / MDT 分歧已裁决）
  且 强迫审核项（危象、科室选择、路径顺序、AI↔线下意见冲突）均已处理
  且 自动处理条目都有原因与审计记录
```
UI 上必须能看见：**"自动处理 N 条"**（范围 / 规则 / 排除项 / 抽样规则）+ 二次确认；
审计里记为独立动作 `auto_accept_batch(reason=...)`，**不得与逐条 `accept` 混淆**
（现在的 `human_touched` 计数就把两者混在一起了）。

## 4. 风险分级自动处理：判据 ↔ 现有字段（可直接落地）

**产品语义**：不要叫"AI 自动审核"或"AI 决定"，而是"**风险分级的自动处理**"——
自动处理不等于医生确认。

| 分级维度 | 代码里已有的判据 | 归属 |
|---|---|---|
| 格式/重复/缺字段 | `_dup()` 去重、`evidence_refs == []`、空 `ai_content` | 规则自动处理，不进主队列 |
| 证据直接 + 无冲突 + 低影响 | `evidence_state == direct`、`triage.conflicts == []`、非科室/路径类 | AI 预处理，**医生抽检** |
| 间接证据 / 低可靠性 / 资料缺口 | `evidence_state in (indirect, missing)`、`reliability.level` 低、`information_gaps` | **医生必审** |
| 影响就医组织 | `target_type in (department_selection, path_step)` | **医生必审**（路径顺序尤其） |
| 危象 / 关键冲突 / AI↔线下意见冲突 | `blocked_by == G1`、`triage.conflicts`、`update_service` 的 AI↔医生差异 | **强制审核**，必要时二次审核 |
| 模型失败 / 部分缺失 | `analysis.mdt.state in (failed, partial)`、卡片 `status != ok` | **强制审核 + 明确告知** |

**三条红线（建议写进规格书）**：
1. 自动处理必须是**可区分状态**，报告与界面**绝不能显示成"医生已确认"**；
2. **不能只按模型置信度放行**（本项目另有理由：模型置信度本就不该出现在决策链里）；
3. 自动处理要**可撤销 + 可抽检**，并展示"自动处理了哪些、依据什么规则"。

## 5. 信息架构（P1/P2）

**默认：待审队列主屏**（删掉左轨重复列表，改为筛选/统计条）
- 单列结构化列表或表格：`病例号 / 主诉 / 风险等级 / 可靠性 / 分析状态 / 待医生处理数 / 更新时间`；
- 默认排序：高风险 → 冲突 → 缺关键证据 → 等待时长；
- 筛选：急症、冲突、缺资料、低可靠性、待复核、分析失败、专科；
- 分页/虚拟滚动（解决 §2.3 的两个上限）。

**点击病例：病例工作区**
- 顶部固定病例上下文 + 返回队列（**保留筛选/排序/滚动位置**）；
- 中间只展开"必审/高风险"条目；低风险条目折叠，并显示**自动处理原因**；
- 证据与原文放**抽屉**；七屏收敛为四区（概览 / 证据与推理 / 审核 / 历史）；
- 右栏从"常驻"改为"上下文抽屉"，避免与主区争注意力。

**批量操作**：只允许覆盖低风险范围，且必须**预览 + 审计 + 可撤销**；
"全部接受并发布"改为「确认自动处理 N 条」。

## 6. 能力缺口（静态扫描的客观结果）

| 项 | 事实 |
|---|---|
| 撤销 / 回退 / 草稿语义 | **0 处**（`撤销`/`回退`/`草稿`/`undo`/`draft` 在 `doctor.html` 中均无） |
| 就近重试 | **0 处**（`重试`/`retry`/`重新分析` 均无；失败只能靠"批量补齐分析"间接恢复） |
| 无障碍/解释性文本 | `aria-` 2 处、`title=` 1 处 → 应用内解释偏少（与评审"帮助与文档 2/4"一致） |
| 每条目固定 5 个操作 | 对 42% 的"患者建议"类条目属于**过度操作**（评分"灵活高效 2/4"的根因） |

## 8. 顺序建议（回答评审的两个问题）

> 先定"队列优先"页面结构，还是先定 AI 自动处理与医生必审的分级规则？

**先定分级规则与状态模型（切片 ①）**：队列的列、排序、筛选、默认展开范围**全部是"什么算待办"的函数**；
分级未定就重构 IA，等于围绕错误的对象重排布局——这正是当前界面的病根。
**可并行**做一件不依赖它的低风险收敛：删左轨重复列表 + 七屏改页签/折叠。
