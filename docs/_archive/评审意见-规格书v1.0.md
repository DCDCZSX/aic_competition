# 《产品细节规格书 v1.0》评审意见

> 评审对象：产品细节规格书：AI 多学科就医辅助系统（最终改进版 v1.0），31 页
> 定位：文档质量明显高于 v0.2；以下意见按"先结构后细节、先战略后实现"排序。
> 标注：🔴 高（会引发答辩/开发翻车）｜🟠 中（定义缺口/一致性）｜🟡 低（表述/排版）

---

## 一、🔴 结构性缺陷（最优先修）

### 1.1 全文存在"三套分类体系"互不对齐
- §1.2 核心用户：5 类人群（挂科难/共病/多意见/术前/疑难）
- §4 目标选择：5 个目标 A-E（挂科/共病/整理意见/术前/疑难）
- §11 行为类型：5 类 A-E（单科/共病/疑难/手术/危象）

三套分类高度相似但**并不等价**：目标 C（整理多个医生意见）没有对应的行为类型；目标 E（疑难）与行为 C/D 重叠；行为 E（危象）又跨到 §8 Guardrail。
**建议**：合并成"一张总表"贯穿全文：`用户目标 → 行为类型(A-E) → 触发规则 → 输出模板`。否则实现时每个模块各自造一套分类，代码与文档都会漂移。

### 1.2 MVP 范围与"1 个月、2-3 人、边学边做"的现实严重脱节
- §33 "v1 必须完成"：患者端 12 项 + AI Core 8 项 + 医生端 10 项 ≈ **30 项**
- 对比 v0.2 曾估算 7 模块 ≈ 22-26 人日；v1.0 增加了智能追问闭环、动态更新、医生端全套、双版本报告，粗估 45+ 人日
- 全文**没有任何"工时 × 人数 × 周数"的可行性假设**，也没有 P0/P1/P2 分级

**建议**：① 文档开头加一行约束声明："比赛版本 = 3 人 × 3 周可交付范围"；② 把 §33 拆成 P0（演示链路依赖）/ P1 / P2；③ 明确砍掉或降级：医生端→演示级、动态更新→v1.1、智能追问→单轮限 3 问。

### 1.3 医生端是最大叙事与验证风险（必须写清"比赛版定位"）
- 队伍**接触不到真实医生**（此前已确认）；而 §14-21 把医生端写成核心工作流，答辩被问"真实医生试用过吗/修改记录数据哪来的"会直接穿帮
- **建议**：① 比赛版把医生端明确定位为"演示级只读审核台（接受/修改/驳回 UI + 记录落库）"，用 1-2 位医学背景同学扮演审核人做概念验证；② 文档新增"验证计划"章节说明替代验证方案，而不是让读者默认有真实医生

### 1.4 缺"验证与评测计划"整章
- §31 质量指标只有目标值，**没有"数据从哪来、怎么测、未达标怎么办"**
- 分诊召回 ≥0.80 需要 n≥30 金标准——目前只有 MDT-5 的 5 例；画像精确率抽 30 例谁标？医学合理性 ≥3.5/5 谁打分？
- **建议**：把《评测实验设计方案》作为一节并入（数据源：公开医患对话集 + 人工标科 + 医学背景同学 checklist），每行指标补三列：评测方法 / 数据来源 / 未达标动作

## 二、🟠 定义缺口（修完结构后逐条补）

### 2.1 画像"完整度门槛"未定义（§7.3）
"关键画像完整度达到门槛"是追问与放行的核心开关，但没有定义：门槛由哪些字段构成？如何打分？未达门槛是阻断还是带 unknown 进入会诊？
**建议**：定义 `completeness = 高影响字段集合的填充率`，给字段清单（主诉/时间线端点/关键检查/主要问题…），并给阈值与两档动作。

### 2.2 危象触发存在两处定义（§8.1 vs §11 E 型）
Guardrail（进分诊前）与行为类型 E（S1 内）语义相同但分处两章，实现时极易变成两套词表。
**建议**：收敛为**单一触发器 + 一份可审计词表**（≥40 条，含"胸痛+大汗"类组合规则），在 §8 唯一声明，§11 E 型引用它。

### 2.3 数据结构的"类型/枚举/示例"缺失（§28）
PatientProfile / TriageResult / SpecialistOpinion / MDTResult / DoctorDecision 只有字段名。
缺：字段类型、枚举值（behavior_type 的取值、relevance 取值、priority 取值）、嵌套关系、JSON 示例。
**建议**：每张 schema 补：类型表 + 一段真实病例的完整 JSON 样例（答辩与开发都吃这套）。

### 2.4 医生"接受/修改/驳回"的粒度未定义（§20-21）
修改是针对"科室入选"还是"单张意见卡"还是"路径/报告"？粒度不同，DoctorDecision 结构与"接受率/修改率"统计口径都不同。
**建议**：定义审核单位 = `决策条目`（科室入选、路径步骤、共识/分歧条、患者建议），每条一个状态。

### 2.5 动态更新与"医生已审核结论"的关系未定义（§24 vs §20/§29）
新资料到达后，医生审核过的版本自动过时：是整份回到"待审核"，还是只标记受影响区？
§29 状态机没有 `更新 → 重新审核` 回路。
**建议**：补一条明确分支："资料更新 → 受影响模块重算 → 版本 +1 → 状态回到待审核（保留医生原意见作为对比）"。

### 2.6 新增模块无质量指标
追问问题有效性、共识/分歧聚合正确性、动态更新后"受影响专科识别"准确率——都没有验收线（v0.2 曾有"分歧检测精确率 ≥0.70、宁少勿多"，v1.0 反而丢了）。
**建议**：§31 补三行：
- 追问：影响分诊/候选集的问题占比 ≥50%（抽 20 例人工判）
- 分歧检测：精确率 ≥0.70（宁少勿多）
- 动态更新：局部重算 vs 全量重跑一致率 ≥90%（抽 10 例）

### 2.7 数据留存与"病历档案化"冲突（§5.2 / §24 vs 合规原则）
动态更新要求病例跨会话持久化为"档案"，与"病历原文不落盘 / 30 天清理 / 一键删除"需要统一：档案存什么（原文 or 仅画像+报告）？医生端访问权限？
**建议**：在合规段明确"档案模式"的存储边界：原文不落盘，落盘的是脱敏画像+各版本报告+审核记录，删除按钮同时清档案。

## 三、🟡 表述与排版

### 3.1 流程图占位
正文大量"此处应有流程图/卡片图"（第 10-12、18、29 页结构以纯文字和箭头堆叠），最终技术方案需要真正的架构图、状态机图、时序图。规格书阶段建议至少补：总体架构图、会诊状态机图、医生审核时序图。

### 3.2 定位与名称一致性
§1.1/§1.2 的"人群画像"与 §37 的"最终产品定义"可以更早收敛；"AI 多学科就医辅助系统"作为作品名过长（规则：作品名称 ≤20 字，建议"多学科就医智助系统"这类 6-8 字方案）。

### 3.3 schema 键名中英注释
`complaint/timeline/...` 等 key 与中文章节没有对应表，建议数据结构节附"键名-含义-取值"三列表。

## 四、值得保留的亮点（别改丢）
- §36 差异化叙事（直接 GPT vs 本系统的决策层对比）非常有力，答辩主线就用它
