# 医生端审核台 UI 设计说明（比赛版 v-competition）

> 配套：《产品开发规格书-比赛版v-competition.md》（本文是它的 §2/§3/§5/§10 的界面层展开）
> 形态：本地 Web 应用（浏览器界面）；**本文只描述设计，不包含任何实现代码**。
> 范围：**全局入口（登录页 + 角色选择）** + 医生端 = **按科室隔离的审核台**（预置医生账号、操作落库 SQLite）。患者注册后提交的病例只进入其确认的主科室；MDT 协作由主科室医生显式授权。
> 风格：**冷静专业医疗风**——蓝白基调、克制留白、信息密度适中，先"可信"后"好看"。
> 说明：登录页为患者端 / 医生端共用入口（对应主文档 §11、规格书 §3.1）；进入患者工作台后的主流程界面属患者端 UI，另行设计说明。本稿详述登录页与医生端审核台。

---

## 1. 设计总则与视觉规范

### 1.1 一句话体验
> 审核人打开一个病例，像"批改作业"一样逐条看 AI 的判断与证据，接受 / 修改 / 驳回，落一条清晰的记录；每一条操作都让观众看得见"人把了关"。

### 1.2 色彩规范（设计 token）

| Token | 色值 | 用途 |
|---|---|---|
| 主色 Medical Blue | `#1B5E8A` | 主按钮、选中态、导航高亮、链接 |
| 主色浅阶 | `#2C7FB8` | hover、次级强调、图标 |
| 背景 Base | `#F4F7FA` | 页面底色 |
| 卡片表面 Surface | `#FFFFFF` | 卡片 / 面板 / 弹层 |
| 分割线 Hairline | `#E2E8F0` | 卡片描边、分隔 |
| 正文 Ink | `#1F2A37` | 主要文字 |
| 次级文字 Ink-2 | `#5B6B7C` | 说明、次要信息 |
| 弱化 Ink-3 | `#8A99A8` | 占位、禁用、角标底色 |
| 确认绿 Confirm | `#2E7D4F` | "接受 / 已确认 / 有明确证据" |
| 警示琥珀 Warn | `#B7791F` | "暂不确定 / 间接证据 / 需复核" |
| 危险红 Danger | `#B3402E` | "驳回 / 危象 / 冲突 / 删除" |
| 信息紫 Info | `#5B4B8A` | "AI 推断"类中性标注（非好非坏） |

- 全界面**色彩面积 <10%**：大面积保持白/浅灰，彩色只用于状态与操作，医疗场景不宜花。
- 危象 / 急症相关只用 Danger 红，且不得只靠颜色传达（必须配文字，见 1.6）。

### 1.3 字体与排版
- 中文字体栈：`"PingFang SC", "Microsoft YaHei", "Noto Sans CJK SC", sans-serif`（跟随系统即可，比赛不引字体文件）。
- 数字/科室代码/时间：`font-variant-numeric: tabular-nums`（或等宽栈），保证表格对位整齐。
- 字号梯度：页面标题 20px / 卡片标题 15px(600) / 正文 14px / 辅助 12px / 角标与徽章 11px。
- 行高 1.6；正文不做两端对齐；中文不加斜体。

### 1.4 布局与间距
- 页面结构：**顶栏(病例上下文) + 左导航(7 屏) + 主内容区**（宽屏再加右轨审核面板）。
- 间距体系：4/8/12/16/24/32（px）；卡片内边距 16-20，卡片间距 16。
- 内容区最大宽度 ~1200px，居中；表格行高紧凑但可读（≥40px 行高）。
- 所有"AI 意见"区块用统一**淡色底 + 左侧竖条**（暖色 token：`--info` / `--accent`）区分"人写的 vs AI 写的"。

**响应式与打印约定（2026-09-15 实现口径，有分档回归测试守着）**：

| 宽度 | 布局 | 关键点 |
|---|---|---|
| ≥1440px | 三轨：左导航 + 主内容 + **右轨审核面板常驻** | 屏 F 里的主区发布镜像隐藏，避免同一操作在屏上出现两次 |
| 1100–1439px | 两轨：左导航 + 主内容 | 右轨收起 → **发布审核版 / 录入线下意见由屏 F 主区承接**（`#rev-publish-inline`） |
| ≤1099px | 单列堆叠（左导航变卡片置顶） | `#rev-body` / `#list-body` 单列 |
| ≤640px | 单列 + 页面内边距收窄到 16px | 顶栏病例号换行显示，不隐藏信息 |
| 打印 | 隐藏顶栏 / 轨道 / 操作条 | 报告折叠段自动全部展开，折叠控件与按钮不打印 |

> **硬约定（踩过坑）**：**右轨里的关键操作必须有主区镜像**。曾经 `<1440px` 时右轨被
> `display:none` 收起，而"发布/录入线下意见"只写在右轨里 → 1366×768 笔记本或投影窗口下
> 医生审完却发不出去。现在由 `tests/test_responsive_layout.py` 在 8 档宽度上守着。

### 1.5 核心组件清单
| 组件 | 设计要点 |
|---|---|
| 角色选择卡 | 登录页两栏大卡（患者演示 / 医生演示）：图标 + 主文案 + 该端能力小字 + 预置账号名；hover 上浮+主色描边 |
| 登录表单 | 账号 + 角色下拉（可选）+ 密码；错误提示用红条"账号或角色不符"；演示可留快捷按钮跳过 |
| 身份条 | 登录后顶栏常驻：`角色 · 账号（如 医生 · doctor）` + 右上[退出登录] |
| 病例卡 | 姓名(脱敏/代号) + 年龄性别 + 行为类型徽章(A-E) + 可靠性等级徽章 + 待审数红点 |
| 状态标签 Pill | 圆角胶囊，彩底 10% 透明度 + 深色文字（见 1.2 语义色） |
| 决策条目卡 | 每条 = 一条可审核结论；头部含目标类型 + 状态；主体含结论/理由/证据引用；底部操作条 |
| 证据引用 Chip | `来源S-1:34` 小胶囊，hover 弹出原文浮层（source_ref 悬停） |
| 证据状态标 | direct 绿 / indirect 琥珀 / missing 灰 / conflict 红 / doctor_confirmed 深绿勾 / awaiting 虚线框 |
| 操作按钮组 | 主要：接受(主色实心)；次要：修改、驳回、暂不确定、请求补资料(描边)；危险：驳回(红描边) |
| 角标 | 页面/导出件常驻 **"AI 生成 · 尚未经医生审核"** 或确认后 **"已由 XX 审核"** |
| 差异对照 | 左右两栏 or 行内 diff：AI 原文（删除线）→ 医生修改后（绿底），附原因 |
| 空态/加载态 | 空态给引导文案；AI 模块加载用骨架屏 + "专科分析中…"进度 |

### 1.6 通用合规元素（所有页面必带）
- 右上或页脚常驻：`AI 生成，尚未经医生审核`（灰底小字）；该病例已被审核确认后才换成绿色 `已审核`。
- 报告预览与导出件同样带角标与免责行（与规格书 §3.3 / §11 一致）。
- 危象提示（若出现）：红色警示条 + 明确文字"疑似急症，请立即就医"，不依赖图标颜色。

## 2. 信息架构（页面地图）

全局入口 + 审核台共 **1 登录入口 + 7 工作屏**，从"选角色 → 列表 → 逐条审核"，符合"入口清晰 → 总览 → 依据 → 决策"的演示叙事：

```
[0] 登录页（角色选择）
   ├─ 进入患者端 ─▶ 患者工作台（见《UI设计说明-患者端.md》：录入/追问/任务/摘要/资料更新）
   └─ 进入医生工作台 ─▶ [A] 病例列表
                        └─ 点击病例 ─▶ [B] 病例总览（画像 + 可靠性 + 待办提示）
                             ├─ [C] 分诊依据（决策链 S1→S3 可视化）
                             ├─ [D] 证据板（时间线 + 判断↔证据关联）
                             ├─ [E] MDT 会诊审阅台 ★（三栏临床决策工作台：患者画像 / 独立研判→分歧→质询→补答 / 证据卡与裁决）
                             ├─ [F] 报告审核工作区 ★核心（逐条决策条目操作 + 录入线下意见）
                             └─ [G] 审核记录与版本（审计日志 / 版本回溯）
```

> 登录后按角色进入不同工作台；顶栏显示当前角色身份（如"演示审核人-医学生"），可随时退出返回登录页。导航在 [B]-[G] 常驻左侧；顶栏显示当前病例代号 + 行为类型 + 可靠等级 + 全局"未审核"角标。
> 分工：**逐科发言/共识分歧等 MDT 过程内容（屏 E）属医生端**；患者端只看到各科结论摘要（见患者端 P8）。

## 3. 逐屏设计说明

### 屏 0：登录页与角色选择（全局入口，主文档 §11 / 规格书 §3.1）
```
┌────────────────────────────────────────────────────────────┐
│  (居中卡片, 白底, 背景浅蓝灰)                                │
│                                                             │
│   🏥  多学科就医智助系统                                      │
│  AI 辅助就医信息整理与多学科决策协作平台                      │
│                                                             │
│  ┌──────────────────┐   ┌──────────────────┐               │
│  │  进入患者端      │   │  进入医生工作台      │              │
│  │  patient     │   │  doctor      │             │
│  │  整理资料 / 就医路径│   │ 病例审核 / 证据审阅│             │
│  │  任务中心 / 就诊后更新│  │ 报告确认 / 线下意见录入│          │
│  └──────────────────┘   └──────────────────┘               │
│                                                             │
│  或：输入预置账号登录           账号 [__________] 角色 [▾]    │
│      密码 [__________]   [登录]                               │
│  ⚠ 本系统为就医辅助演示，不提供诊断/处方；急症请立即就医。      │
└────────────────────────────────────────────────────────────┘
```
- 两种进入方式都保留：**角色卡片快捷入口**（一键演示，最优先展示）+ **账号/角色登录**（体现真实产品形态，后台仍按角色执行权限判断——不能只做前端跳转）。
- 角色卡视觉：左右两栏对等（患者蓝 / 医生深蓝绿），下方一行小字点明该端能力；悬停轻微上浮 + 主色描边。
- 患者角色文案强调"资料整理 + 就医任务 + 就诊后资料更新"，医生角色强调"审核 + 证据 + 报告确认 + 线下意见录入"——一眼区分两端职责。
- 顶栏登录后显示身份：如"医生 · doctor（演示审核人）"，右上角[退出登录]返回本页。
- 数据来源：医生账号由部署配置预置，并绑定 `department_code`；可为总审账号配置 `access_scope=all` 查看全量病例。患者账号通过患者端注册创建。科室医生只能看到已授权给本人且属于其科室范围的病例，前端提示不替代后端权限校验。
- 病例分流：患者提交前确认主科室，系统只向该科室的可用医生建立访问授权；无可用医生时明确提示，不把病例静默暴露给其他科室。需要 MDT 时，由主科室医生选择协作科室，系统仅向对应的已配置医生授予该病例访问权。
- 合规：登录前不能访问任何病例数据（前端路由守卫 + 后端权限双重校验）；登录页即放置免责与急症提示。

### 屏 A：病例列表
```
┌────────────────────────────────────────────────────────────┐
│ 顶栏: 多学科就医智助系统 · 医生审核台    [演示审核人-医学生]   │
├────────┬───────────────────────────────────────────────────┤
│ 筛选    │  病例列表(按待审优先排序)                          │
│ [全部▾] │  ┌─────────────────────────────────────────────┐  │
│ [待审核]│  │ 病例 #C001 女58  B·多病共病  可靠中   ●待审3  │  │
│ [已确认]│  │ 主诉: 视物模糊3月, 下肢浮肿1周   内分泌牵头   │  │
│        │  └─────────────────────────────────────────────┘  │
│ [搜索]  │  (列表行: 卡片式, 每行显示关键摘要, 点击进入[B])    │
├────────┴───────────────────────────────────────────────────┤
│ 合规条: AI 生成 · 尚未经医生审核                              │
└────────────────────────────────────────────────────────────┘
```
- 数据来源：规格书病例库 + `DoctorDecision` 聚合的待审计数。
- 状态：待审核(蓝点计数) / 已确认(绿勾) / 已驳回(红) / 暂不确定(琥珀)。
- 文案：行内给"1 句主诉 + 牵头科 + 可靠等级"，审核人扫一眼能判断优先级。
- **分析状态徽章（2026-09-14 新增）**：每行同时显示该病例的多学科分析状态——
  `分析中`（琥珀）/ `分析就绪`（绿）/ `部分未完成`（红）/ `分析失败`（红）/ `未分析`（灰）。
  医生据此决定"现在能审"还是"等它跑完再审"，不必点进去猜。

```
│ 列表工具条: [状态▾] [刷新] [批量补齐分析]   共 N 例（按待审条数排序） │
│ 病例 #C001 女58  B·多病共病  可靠中  ●待审3  分析就绪              │
│ 病例 #C002 男61  C·诊断未明  可靠低  ●待审5  分析中                │
```

- **批量补齐分析**：点一次会把"分析未完成"的病例排队进后台任务（每次最多 3 例，已在跑/已完成的自动跳过），
  请求立即返回，列表状态随后自动从 `分析中 → 分析就绪`；医生可以先做别的事，不阻塞操作。
  - **"部分未完成"也会被排进去**（2026-09-15 实现口径）：只要有一个科室没跑出意见卡，该例就算未完成，
    重排时只重跑多学科那一步，不会把已经好的画像/分诊结果重算一遍；
  - 后台任务"卡在分析中"超过 10 分钟（例如服务重启把线程丢了）视为已失效，允许重新排队。

### 屏 E：多学科审阅（逐科失败的口径）
```
第 1 轮：独立研判（互相不可见，仅基于画像）
  内分泌科  事实：…  推断：…
  血液科    本次未完成分析（意见卡解析失败（输出被长度截断））—— 不影响其余科室，
            可在病例列表用「批量补齐分析」重跑该例
  眼科      事实：…  推断：…
```
- 失败的科室**保留在固定位置上如实说明原因**，不用沉默的空卡片充数；其余科室结论照常呈现与审核。
- 若某科结论是"格式修复后恢复"的（输出曾被截断），卡片上会带一行"说明：…已按已写出的字段恢复"，
  医生据此知道该科条目可能不全，必要时点「批量补齐分析」重跑。

├───────────┬─────────────────────────────────────────┤

│ · 主诉     │  ╭────────────────────────────────╮     │

│ · 已知疾病 │  │ 2. 共识/分歧含 1 条冲突（[E]）     │     │

- 画像卡字段对应规格书 `PatientProfile`；每条 hover 显示原文出处。
- 明确标注：紫 "AI 推断" / 灰 "待确认" / 正常色 "原文记载"（事实-推断-待确认三分可视化）。

### 屏 C：分诊依据（评审最看重的"可解释"屏）
```
决策链(自上而下流水线视图):
 [S1 规则命中] ──▶ [S2 模型发言] ──▶ [S3 编排校验] ──▶ 结果
 内分泌科 strong:      采纳(无反驳)         必选✓
   信号: "糖尿病5年"    肾内科 medium → 采纳  入选✓
 肾内科 medium         眼科 medium → 采纳   入选✓
 眼科 medium           (模型新增 0 科)      牵头=内分泌✓
 心血管 weak → 已剔除   冲突: 无            总数3 ≤6 ✓
 decision_path: rule-dominant                [分诊结果详情]
```
- 每科显示：权重徽章、命中的具体信号文本、模型采纳/补充/反驳记录、入选理由。
- 若有 conflict_log（模型反驳 strong），红条展示"分歧保留并进入报告分歧区"。
- 数据来源：规格书 `TriageResult` + decision_path + signals。
- 这是答辩/录屏的"技术感"截图点，务必做成**可展开的流水线**而不是一坨文字。

### 屏 D：证据板
```
时间线(横向/纵向): 症状3月前 ─ 确诊5年 ─ 尿蛋白++ ─ 拟眼底检查
┌──────────────────────────────────────────────┐
│ 判断: "需排查糖尿病视网膜病变"（眼科）          │
│   ├─ 支持: S-2:12 视物模糊3月渐重   [direct]   │
│   ├─ 缺失: 眼底检查结果             [missing]  │
│   └─ 反向: 无                        ─        │
│ evidence_state: awaiting_doctor  [请求补资料]  │
└──────────────────────────────────────────────┘
```
- 只做时间线 + 判断↔证据关联两块（规格书 §6.2 比赛版范围）；what-if 按钮置灰并注"P1"或隐藏。
- 关键规则：**"相关"与"支持"分离**——仅同源直引标 direct，否则标 indirect/missing。

### 屏 E：MDT 会诊审阅台（三栏临床决策工作台，★医生核心屏）
> 定位升级：**逐科独立研判、证据、共识/分歧/质询是给医生看的过程**（患者端 P8 只给摘要卡）。本屏采用"临床决策工作台"三栏布局，**不做成"Agent 群聊"式界面**——评委最反感"几个 ChatGPT 窗口轮流说话"。

```
┌──────────────────────────────────────────────────────────────────┐
│ 病例 #C001 · MDT 审阅 · 参与: 内分泌(牵头)/肾内/眼科  [▶ 播放过程]  │
├──────────────┬───────────────────────────────┬───────────────────┤
│ 左栏: 患者画像  │ 中栏: MDT 工作台(过程)          │ 右栏: 证据与决策    │
│ · 主诉/时间线  │ ┌─ 第 1 轮: 独立研判 ────────┐ │ · 支持证据          │
│ · 检查/用药   │ │ 内分泌/肾内/眼科各出意见卡(    │ │   (患者证据 S-1:34) │
│ · 信息缺口   │ │  互相不可见, 仅基于画像)      │ │ · 反对证据          │
│ (可展开原文)  │ └──────────────────────────┘ │ │   (外部证据条目)    │
│             │ ┌─ 分歧: 眼科优先级 ──────────┐ │ · 争议点 1 条        │
│             │ │ 眼科: 建议先查眼底            │ │ · 风险 / 不确定性   │
│             │ │ 肾内: 先查肾功再会诊          │ │                    │
│             │ └──────────────────────────┘ │ · 待医生裁决: 1 条   │
│             │ ┌─ 质询(第 2 轮) ────────────┐ │                    │
│             │ │ Q: 眼底缺失时"眼科优先"依据  │ │ [接受][修改][驳回]   │
│             │ │ 是否充分? 需补充眼底检查结果  │ │ [加入待确认问题]     │
│             │ │ → 各科补答 · 结论维持待复核   │ │                    │
│             │ └──────────────────────────┘ │                    │
└──────────────┴───────────────────────────────┴───────────────────┘
```
- 布局原则（对应早期外部评审输入中的"临床决策工作台"建议，按红线改写）：**左=客观资料、中=推理过程、右=证据与裁决**——让医生一眼看到"每条结论的依据和分歧点在哪"。
- 数据来源：`PatientProfile` + `SpecialistOpinionCard` + `MDTAggregation`（含质询记录）+ 证据卡（支持/反对双列）。
- **质询展示（红线版）**：中栏显示"第 1 轮独立研判 → 分歧 → 质询 → 各科补答 → 需医生复核"，**只显示"哪些判断被质疑、缺什么证据、是否维持"，不显示任何概率/置信度数字**。
- "▶ 播放过程"= 演示增强：按时间顺序展开 独立研判→分歧出现→质询→补答，帮助评委理解决策链；可暂停。
- 右栏每张证据卡 = 支持/反对双列（主文档 §9.4）；无外部证据时显示"暂无可靠外部依据"，不伪造文献。
- 分歧条提供"一键把此分歧加入报告待医生确认问题清单"——演示亮点。
- 若存在"AI 推断 vs 已有医生线下意见"差异，也在右栏用差异对照呈现（数据来自屏 F 录入的线下意见）。

### 屏 F：报告审核工作区（★核心屏）
```
┌──────────────────────────────────────────────────────┐
│ 报告审核版 · 完整报告(13 段见主文档 §12.2)   [导出PDF]   │
│ 角标: AI 生成 · 尚未经医生审核                          │
├──────────────────────────────────────────────────────┤
│ 逐条决策条目（列表只保留摘要）:                         │
│ ┌───────────────────────────────────────────────┐    │
│ │ ① 科室选择: 牵头 内分泌科     [查看详情][接受]       │    │
│ │ ② 就医路径: 先查 眼底/肾功     [查看详情][修改]       │    │
│ │ ③ 患者沟通建议: 就诊前准备     [查看详情][驳回]       │    │
│ │ ④ 共识与分歧: 有创血管评估     [查看详情][暂不确定]   │    │
│ └───────────────────────────────────────────────┘    │
│ 点击“查看详情”后，工作区切换为单条审核详情:           │
│ AI 初稿 / 判断依据 / 证据 / 处理提示 / 审核操作         │
│ [返回审核列表]                                         │
│ 底部: 全部条目完成后 → [确认发布审核版报告] (需 ≥1 条人   │
│       工痕迹或全部接受, 发布后状态回填为已确认+角标变绿)   │
│ 就诊后: [录入线下实际意见] ← 患者就诊后, 由审核人/医院录入 │
│        真实医生意见 → 生成 "AI建议 vs 医生意见" 对照        │
└──────────────────────────────────────────────────────┘
```
- 审核单位 = **决策条目**（规格书 §5.6：科室选择 / 就医路径 / 共识与分歧 / 患者沟通建议）。内部枚举只保留在接口和审计数据中，不直接展示给医生。
- 审核列表只显示标题、类型、责任级别、状态和 AI 初稿摘要；点击“查看详情”进入同一工作台内的单条详情视图，正文使用可读字号，保留“返回审核列表”入口。
- 医生端使用“AI 初稿”“待医生判断”“审核后表述”等医生视角文案；患者侧“向医生确认……”只在患者端保留，审核详情中转换为“待医生判断：……”。
- "修改"弹窗：显示 AI 原文 → 医生改写 → **原因必填**；落 `DoctorDecision(action=modify, before/after/reason)`。
- "驳回"同样原因必填；"暂不确定"给琥珀状态不入报告待确认区。
- 确认发布后：状态 → `doctor_confirmed`，报告角标切绿，`version+1`（若此前有更新）。
- **[录入线下实际意见]（就诊后闭环，医生职责）**：患者线下就诊后，由医生端（审核人）录入/导入真实医生意见（来源=医生上传/医院文档），系统据此生成 **AI 建议 vs 医生意见** 对照（一致 / 差异类型 / 差异原因），并触发受影响模块局部重算与变化摘要（对应患者端 P10-P11）。**患者端不承担"替医生写意见"**——患者只补充他手上有的新资料。

**发布入口的"双入口"约定（2026-09-15 修复真实缺陷）**：
- 现状问题：`.rail-right` 在 **<1440px 会被 CSS 收起**，而"确认发布审核版 / 全部接受并发布 / 录入线下意见"
  原来**只写在右轨**里 → 1366×768（常见笔记本）或投影窗口下，医生审完却**发不出去**，流程卡死。
- 现在：同一份面板由 `publishPanelHtml(sum, canPublish, pfx)` 渲染到**两处**——右轨 `#rev-publish`（≥1440px 常驻）
  与屏 F 主区的 `#rev-publish-inline`（<1440px 兜底）；两处 id 用前缀区分（`rail-` / `inline-`），
  录入按钮自带前缀（`submitOpinion('rail')` / `submitOpinion('inline')`），不会写错输入框。
- 一般原则：**凡是"右轨里的关键操作"，都必须有主区镜像**；右轨只做宽屏快捷面板，不能是唯一入口。

### 屏 G：审核记录与版本
```
版本 v3 (最新)  ── v2(医生修改后) ── v1(AI 原稿)
每次操作时间线(审计日志):
 09-12 14:02  修改 科室入选-牵头 内分泌科  原因: 补充血糖评估优先级  (医学生)
 09-12 14:00  接受 路径步骤-先查眼底
 09-11 20:15  请求补资料 → 患者已上传新检查(尿蛋白) → 触发局部重算 → v3
```
- 对应规格书 `DoctorDecision` + version + created_at；展示"资料更新→重算→受影响条目回待审"的痕迹。
- 审核记录同时显示 `content_revision`。旧修订决定标记为"已过期"并保留在历史中；病例队列和审核页显示资料更新重新打开的具体条目，未受影响科室不重复进入待审。

## 4. 审核操作状态机（界面层可见规则）

```
每条决策条目:
  awaiting(待审) ─接受→ confirmed(绿勾)
       │  └─修改→ modified(展示 before/after, 绿勾+铅笔标) → confirmed
       ├─驳回→ rejected(红, 原因必填, 该条不进报告)
       └─暂不确定→ uncertain(琥珀, 进"待医生确认问题清单")
任意资料更新 → 受影响条目回到 awaiting(保留医生原意见对比) → 重新审
全部条目终态后 → 报告可 [确认发布] → 顶栏角标 "已审核"
```
- 界面必须让观众随时看懂"当前这版是 AI 原稿还是医生已把关"——靠角标 + 条目状态色双保险。

## 5. 演示走查脚本（3-4 分钟，对应规格书 §2 / §3）

1. **登录选角色**（15s）：打开系统 → 登录页出现，点"进入医生工作台"（doctor），口播"系统分患者/医生两个角色，医生进入审核台"。
2. **列表**（15s）：从病例列表点开 #C001，口播"这是 AI 分诊认为需要多学科的一个共病病例"。
3. **总览+依据**（35s）：画像卡 hover 指出处 → 切"分诊依据"展示 S1 规则信号，口播"每条推荐都有可展开的规则依据"。
4. **MDT 会诊审阅（50s）**：屏 E 三栏工作台 → "▶ 播放过程"顺序展开 独立研判→分歧出现→质询→各科补答，停在 1 条分歧/质询上，点"加入待确认问题"，口播"各科先独立判断、分歧如实呈现、AI 自己也会被质询——过程给医生看，患者只拿结论"（**全程无概率数字**）。
5. **逐条审核**（50s）：接受 2 条 → 修改 1 条（弹窗填原因）→ 驳回 1 条，口播"每条操作都留痕"。
6. **发布+版本**（20s）：确认发布 → 角标变绿 → 切审核记录页展示审计时间线收尾。
7. **就诊后对照**（30s）：患者线下就诊上传新资料后，医生端 [录入线下实际意见] → 展示"AI 建议 vs 医生意见"对照 + 变化摘要，口播"AI 和真实意见的差异也如实呈现"。
8. 全程顶栏与导出件可见"AI 生成·尚未经医生审核 → 已审核"的合规转场。

> 录屏素材可直接复用于比赛视频"登录 + 医生把关 + 就诊后对照"段；该段与患者端演示（从"进入患者端"开始录）合起来 = 完整 P0 叙事。分工建议：患者端讲"就医前决策辅助"、医生端讲"MDT 审阅 + 医生把关 + 对照闭环"，避免重复。
