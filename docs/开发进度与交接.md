## 1. 一分钟看懂现状

**能跑通的链路（已验证的现状）**：
```
浏览器 → backend/templates/index.html（轮询式前端）
      → POST /api/start_consultation（姓名/年龄/性别/病历/主要问题）
      → MDTService 内存会话 + 后台线程
      → MDTAgents.controller_agent（LLM 选科，失败回退关键词规则）
      → specialist_agent 逐科分析 → coordinator_agent 整合
      → GET /api/get_discussion_status/<id> 轮询取结果
```
**启动**：`python start_mdt.py`（或 `cd backend && python app.py`）→ http://localhost:5000

**三个必须先知道的坑**：
1. 🔴 `backend/services/ai_service.py:10` **明文硬编码 API Key**（且已随目录多处复制）→ 提交前必须改为环境变量，并在控制台**作废重建**该 Key。
2. 🟠 `frontend/`（React 版）**是坏的**：没有 `package.json`、调用不存在的 `/api/conduct_discussion` → 已于 2026-09-09 归档到 `_legacy/`，**不要从归档区移回或在其上开发**。
3. 🟠 `CHAIS/README.md` **与实现严重不符**（写了 WebSocket、并行会诊、知识库检索等不存在的能力）→ 材料中不得照抄，需按真实实现重写。

5. **`CHAIS/README.md`**：内容与实现不符；**改它必须先看完 §6 安全待办**，重写为真实能力（防止答辩被打假）。
6. **产品红线（写代码时同样适用）**：
   - 不出诊断结论、不出处方/剂量；
   - 不展示模型自报概率/置信度给用户（规格书 §4.3、主文档 §2.5）；
   - 不做"AI 主动开检查"，医疗行为只输出"建议向医生确认是否需要"；
   - 质询/第二轮**不得输出概率数字**（规格书 §6.3）。

pip install -r requirements.txt              # 根目录版

**分支命名**：`feature/<模块名>`、`fix/<问题>`、`chore/<杂项>`、`docs/<文档>`

**每个小增量的标准流程**（小步提交，PR 合入）：

```bash
git fetch origin --prune
git checkout -b <type>/<name> origin/main     # 从最新主干切分支
# …只做一件事，按任务验收列自测…
git add -A
git commit -m "<type>(<scope>): <说明>"
git push -u origin <type>/<name>
# 创建 PR → 目标分支 main（附验收证据：命令输出/截图/评测数字）
# 合入后：git checkout main && git pull
```

**提交信息规范**：`<type>(<scope>): <subject>`
- type：`feat` 新功能 / `fix` 修缺陷 / `chore` 杂项 / `docs` 文档 / `refactor` 重构 / `test` 测试
- 示例：`feat(guardrail): 危象词表扩充至 42 条并加组合规则`

**PR 粒度**：**一个小功能/修复 = 一个 PR**；同一功能内的多个小改动可以在**同一分支、多个 commit**里，避免每个 commit 都开新 PR 造成噪音。PR 描述必须包含：改了什么 / 怎么验证 / 是否触碰红线。

**提交纪律（硬约束）**：
1. **绝不直接 push `main`**；
2. **绝不提交密钥与真实病例数据**——`.gitignore` 已挡 `.env`、`MDT-5*.csv`、`eval_out/`、`knowledge_base/`、`offline_packages*`，新增大文件前先确认是否该忽略；
3. 每个 PR 合入后**必须**回来更新本文件 §5 状态与 §9 变更日志；
4. 触碰 §3 禁改区的改动，PR 描述里写明队友确认。
